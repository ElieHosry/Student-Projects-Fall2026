KOPI-TWIN (student proposal)

Assessment: ✅ Fit · Category: Education + Training · Assessed: 2026-09-21 · Status: awaiting instructor approval · Runner-up category: Immersive Experience

Proposal (as submitted): Kopi Twin is a mobile augmented-reality training app that turns an ordinary table into a simulated kopitiam drink workstation for new food-service employees — trainees practise preparing and serving orders without occupying a stall or using real ingredients. Unlike video tutorials or fixed step-by-step guides, it uses a real-time simulation to generate customer orders, manage virtual ingredients, track recipe states and introduce changing workplace conditions. Trainees do guided lessons, then timed peak-hour scenarios balancing speed, accuracy and waste; performance is scored on procedural accuracy, completion time, incorrect actions and simulated ingredient usage. The POC focuses on traditional kopi, but the data-driven training system can extend to other workstations. Named technical features: a native C++ digital-twin core on ARCore's NDK (C API) converting a live camera scan into a persistent, bounded spatial-anchor map that survives across sessions; a data-driven object system (real-world anchors carry swappable behaviour definitions in data files, so the same engine runs different scenarios without code changes — swap JSON/txt instead of hard-coding); user interaction with the object system (handle objects via a button press); and a bounded-space digital-twin (a defined playable area with persistent anchor placement). Loop: a local native C++ update loop drives the AR session every frame — pull ARCore pose/plane data, update anchored virtual-object states, run the interaction/grading logic — performant enough for a live camera feed on-device. Tool: a content/scenario editor letting a non-programmer (a recipe designer or safety trainer) define anchor points, object behaviours and pass/fail interaction rules as data. Design features: guided AR training (instructions beside the relevant virtual equipment); peak-hour simulation (simultaneous orders, limited ingredients, time pressure); immediate error feedback (wrong ingredients/quantities/sequences/skipped steps); and a performance & competency dashboard (accuracy, completion time, compliance, simulated waste).

Note on category: filed under Education + Training — the product is a training simulator with learning objectives and measurable competency (guided lessons → assessed peak-hour scenarios → a competency dashboard); the pedagogy is the product. Runner-up Immersive Experience (the AR medium) — but the goal is measurable skill acquisition, not atmosphere, so Education + Training is the better home. (Not Simulator: there is no system-modelling/physics simulation as the product — the simulation exists to train a procedure.)

Scope & risk note (advisory, not a blocking condition): persistent cross-session AR anchors + a bounded digital twin + a data-driven scenario system + peak-hour simulation + a scenario editor + a competency dashboard is a large surface, and this is a genuine 3D/AR project (the "strong students only" row); the persistent-anchor AR core on the ARCore NDK is the key risk. Scope the floor to the kopi POC on one bounded table with the C++ AR loop, the data-driven object system, one guided lesson and the grading, and treat cross-session anchor persistence, peak-hour and the full dashboard as the stretch. (ARCore's NDK C API is a low-level platform API — permitted, like SDL/OpenGL ES — not a disallowed engine.)

References:

  • Bartender VR Simulator on Steam (a drink-preparation training simulator: learn recipes in guided modes, then timed orders scored on accuracy and speed, with a completion certificate and a "Pro Mode" — the food-service drink-prep training precedent)
  • Diageo Bar Academy (an industry bartending training platform with accredited skills courses and a virtual-bar experience — the real-world food-service training-with-competency precedent)
  • ARCore SDK for Android NDK (C) — Google (the official native C API for camera pose/plane tracking and persistent anchors that the digital-twin core is built on — the AR-anchor tech precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — ARCore NDK on-device; device: Pixel 9a) — a camera-driven AR app; the Native PC build is the development/tools vehicle (the scenario editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts, progress sync and the trainer/competency dashboard data.
Front end: The AR camera view with virtual kopitiam objects rendered over the live feed (anchored cups, ingredients, equipment), the guided-instruction overlays, the order/timer/error-feedback HUD and the competency dashboard. Languages: Native — Kotlin Native Android UI + the C++ engine (and the ARCore NDK C API) via JNI (Android Studio); OpenGL ES for the AR object rendering in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/scenario-editor build.
Back end: The native C++ per-frame loop (pull ARCore pose/plane → update anchored virtual-object states → run the order/recipe simulation + interaction/grading), the data-driven object/behaviour system, and the bounded persistent-anchor map; plus accounts/progress/dashboard data. Languages: C++ (loop + simulation + grading); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts / progress-sync / trainer-dashboard seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — every frame it pulls ARCore pose/plane data, updates the anchored virtual-object states (order queue, virtual ingredients, recipe states, changing conditions), and runs the interaction + grading logic, sustaining a live camera feed on-device.
  • Data-driven: customer orders, recipes/recipe-states, the per-anchor object behaviours, scenario definitions and the pass/fail grading rules are all data (JSON/txt), so a new drink, scenario or even a different workstation is a data change — not engine code.
  • 2D: the guided-instruction overlays, order/timer/error HUD and the competency dashboard are custom 2D rendering — satisfying the 2D gate. 3D: ✅ central — the anchored virtual objects rendered in AR world space + the persistent bounded anchor map (strong-students; the key risk). Networking: progress/dashboard sync is async client↔︎cloud (Application Communication ✅), so a bespoke Networking System is optional (🔵).
  • Custom tool: the content/scenario editor — a non-programmer defines anchor points, object behaviours and pass/fail interaction rules as data, without touching the C++ engine.
  • External DB: accounts, progress history and the competency-dashboard data. Auth ⏭️: trainee/trainer accounts. Analytics ⏭️: optional — cross-trainee competency trends (the per-trainee dashboard is the team's own in-app analytics via G10).

Track Goals & Team Composition

Recommended composition: 6 CS + 2 Design + 1 Art (9) — the instructional design surface is large (the guided-lesson curriculum, the grading/competency rubric, the peak-hour scenario design, the error-feedback design and the wayfinding-free AR UX), so two designers own the design + UI/UX; one artist can carry the virtual kopitiam objects (cups, ingredients, equipment) as AR assets plus the instruction/HUD/dashboard visuals (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf).
