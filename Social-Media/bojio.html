BoJio (student proposal)

Assessment: ✅ Fit · Category: Social Media · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): BoJio is a mobile social discovery + group-planning app that turns interesting activities into fair, practical outings. Users discover activities via a photo-first feed or real-world venue data, save them, and hit "Plan This" to create a group outing; the group provides locations, availability, budget, interests and travel preferences. An AI-assisted recommendation component interprets preferences and retrieves activities, real-world place/travel data supply venue + journey info, and a performant C++ planning engine evaluates constraints (time, budget, travel distance, group fairness) to generate multiple feasible itineraries; users compare plans, see trade-offs, pick one, and view it as a map + timeline with reminders. The architecture separates recommendation, external-data integration and deterministic C++ planning so each subsystem is testable independently. Named load-bearing C++: a Multi-Objective C++ Itinerary Planner — receives a structured PlanningProblem, removes activities violating hard constraints (availability, opening hours, budget, travel feasibility; constraint-satisfaction with forward-checking / AC-3 pruning), then evaluates meeting points + activity sequences against weighted soft objectives (group travel fairness, preference match, total travel time, cost, activity diversity) via heuristic search, and returns the ranked Top-K itineraries. Named technical features: the planner; offline-aware local caching + sync (Android Room cache for feeds/saved/recent plans, shown immediately while refreshing); vector-based semantic retrieval (preferences + activity descriptions → embeddings in PostgreSQL + pgvector, similarity search matching intent — "something chill and creative" → pottery / art jamming / board-game cafés); and real-world geospatial + travel integration (Google Places + Routes + geospatial queries normalised into a common internal format). Tool: a planning Simulator + Config Tool (synthetic groups/locations/budgets/preferences, edit activity data, configure planner weights/constraints, run the engine, inspect Top-K + score breakdowns; edge-cases like conflicting schedules / impossible budgets / unfair travel; planner params + activity data as external config). Design features: photo-first social discovery; the "Plan This" group flow (must-do vs optional); alternative-plan comparison (Balanced / Fairest Travel / Lowest Cost / Best Preference Match, vote + select); and a visual itinerary + explanation (timeline + map + warnings + group-fit indicators). Team: 6 CS + 1 Design + 0 Art.

Note (category): BoJio's front is social — a photo-first community feed, friends, the "Plan This" group flow and collaborative voting — so it is assessed as Social Media; the C++ multi-objective planner, semantic retrieval and external-data integration are the engine behind the social planning. (A Visualization & Analytics reading was considered for the planner + comparison/trade-off views.)

Note (module completeness): the design already leans on a backend + PostgreSQL/pgvector + Google Places/Routes — this is exactly the module's model (external DB mandatory; a Linux server set up by M2, full use T2; Firebase optional for auth). Platform: it's an explicit Android app (Room cache) — Native Android, Pixel 9a. Scope caution: the ambitions are broad (a real constraint-satisfaction planner + a vector-retrieval pipeline + external-API integration + offline sync); make the deterministic C++ planner the load-bearing star and let the AI-retrieval + full offline-sync flex (see scope note).

References:

  • Meetup (the benchmark for discovering and organising group activities/events — browse activities by interest/location on a map, save them and coordinate a group — the social-discovery + group-outing precedent)
  • Wanderlog — collaborative trip planner (a shared itinerary app where a group co-plans, plots stops on an interactive map, and views the plan on a timeline — the collaborative-itinerary + map/timeline precedent)
  • Pinterest (the photo-first visual discovery platform — explore and save ideas through images rather than text-first search — the photo-first-feed + save precedent)

Back end: C++ + services — the deterministic multi-objective planner (hard-constraint pruning via forward-checking/AC-3, weighted soft-objective scoring, heuristic search, Top-K ranking) — plus a Linux server with PostgreSQL/pgvector (semantic vector retrieval), the Google Places/Routes integration normalised into a common format, and the Android Room offline cache + sync. Languages: C++ (the planning service — load-bearing); backend + pgvector on the Linux server; Firebase optional.
Backend scope: Client + services now, server-hosted (T2) — the planner + retrieval + external-data seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ planning service is the star — it ingests a PlanningProblem, prunes hard-constraint-violating candidates (forward-checking / AC-3), scores meeting points + sequences against weighted soft objectives (fairness, preference, travel, cost, diversity) via heuristic search, and returns ranked Top-K itineraries; it is deterministic and the app's main performance-sensitive component.
  • Data-driven: planner weights + constraints, activity definitions, and the group/preference schema are all external config/data — a new weight or activity is a data change (authored in the simulator/config tool).
  • 2D: the feed, the comparison cards, and the synchronised map + timeline with travel legs/timings/costs (custom-rendered) satisfy the 2D gate. 3D: not needed.
  • Front-end + Back-end: a genuine split — Android client (+ Room cache) over a C++ planner + Linux/pgvector backend + external APIs; the fetch/sync + external-data flows are Application Communication ✅.
  • Custom tool: the planning Simulator + Config Tool — synthetic groups/activities, tunable planner weights/constraints, run + inspect Top-K with score breakdowns, and edge-case testing.
  • Networking: asynchronous social (share/vote/sync), no real-time multiplayer, so a Networking System is optional (🔵). External DB: central (pgvector + normalised place data + plans/social). Auth ⏭️ / Analytics ⏭️: accounts + engagement analytics are natural but module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 0 Art (8) — as proposed, and workable: a planning/social utility app has a light-to-moderate art surface (the photo-first feed uses user/venue photos, so the design work is UI, the comparison cards, the map/timeline styling and iconography), which the D11 conditional can carry. That said, a solo designer + 0 artists is the case the design pool flags ("must ask the instructor which conditional bends", see design-goals-pool.pdf), and the design/UX load here is heavy — the "Plan This" input flow, the alternative-plan comparison UX (making trade-offs legible), and the explanation/warnings design are the make-or-break of the product — so a 2nd designer is recommended (one owning the discovery/social + planning-input UX, the other the comparison/explanation UX + the D11 visual surface). Scope note (advisory): a real multi-objective constraint-satisfaction planner + a vector-retrieval pipeline + external-API integration + offline sync + a simulator tool is a large, ambitious CS scope — the deterministic C++ planner (hard constraints + weighted scoring + Top-K) + the simulator tool is the load-bearing star and the M1/M2 floor; make the AI/semantic retrieval and full offline-sync the stretch (a keyword/filter retrieval is an acceptable fallback if pgvector embeddings slip). Getting the PlanningProblem schema + planner architecture right early (as the team's own "separate subsystems" plan intends) is the single biggest de-risker.
