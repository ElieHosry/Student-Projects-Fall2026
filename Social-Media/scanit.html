ScanIT - Team01 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Social Media · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A native Android shopping assistant that identifies products, compares current prices across retailers, and suggests alternatives from vague requirements. Users scan a barcode/label or search conversationally (e.g. "small black headphones with strong bass under $150"), refine by budget/colour/size/features/brand, and contribute updated prices, availability and product info — a community-driven price database with review/verification before data becomes trusted. Kotlin provides the native Android shell/UI; the performance-critical search & recommendation core is C++ via JNI. Named features: camera-assisted product identification (barcode + OCR); conversational hybrid search (intent extraction, remembered preferences, follow-up questions); a real-time C++ recommendation engine (filter → compare → rank); and a CRUD/crowdsourced backend with multi-store price comparison. Custom tool: an ImGui interface to monitor/test components, change search parameters, trigger searches, view API responses and debug the backend. Focus is current prices (not historical tracking), with explanations of why each result matches.

Category note: filed under Social Media — the load-bearing C++ piece is a ranking/recommendation service over community-contributed content with moderation, which is the Social Media pool's spine (matching/ranking, search & discovery, moderation, Firebase). Runner-up category: CMS (the crowdsourced contribute → verify → trusted-data workflow), which lacks a ranking/recommendation goal and so fits less well.

Adjustments required for approval:

  • Clear the 2D gate with a genuinely custom-rendered data-display surface. A native Kotlin app built purely from Android widgets/RecyclerViews would collapse into ordinary CRUD and fail the module's 2D requirement. Render at least the price-comparison / savings-breakdown view (retailer cards, savings pills, a simple price bar/plot) in OpenGL ES inside a GLSurfaceView, drawn by the C++/render layer — not stock widgets.
  • The recommendation engine must be the team's own load-bearing C++ service. The filter → compare → rank → "explain the match" pipeline (and the ranking behind conversational refinement) must be benchmarked C++ the team wrote. A library/model may extract intents from the conversational query, but an external "AI"/LLM API must not be the engine that does the matching/ranking (category guard-rail: the backend cannot be someone else's service).
  • Be realistic about live retailer prices. Real multi-retailer price APIs are mostly unavailable or paid, and scraping often violates terms of service. Base the project on the crowdsourced database + a seeded/mock (or legitimately available) retailer dataset; treat any live feed as a bonus, not a dependency.

References:

  • ShopSavvy — Wikipedia (barcode-scanning shopping app: finds online & local stores, compares prices, shows reviews/deals)
  • PriceRunner — Wikipedia (price-comparison service matching retailer prices against a backend DB via fuzzy auto-matching + manual admin verification)
  • Google Lens — Wikipedia (camera-assisted product identification: reads barcodes/QR/labels and returns product & shopping results)

How each requirement applies:

Platform fit: Main: Native mobile — the project is a native Android app (Kotlin UI + the C++ core via JNI), camera-first and touch-first (device: Pixel 9a); the Native PC build is the development/debug and custom-tools vehicle (no web target this trimester). Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: Scanner screen (camera), conversational/multimodal search bar, refine chips, and the multi-store price-comparison sheet (retailer cards, stock badges, savings pills) with a custom-rendered price/savings view; plus the crowdsourced contribute/verify screens (OpenGL ES for the custom data-display surface). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES) for the PC dev/debug build; Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The C++ recommendation service (filter → compare → rank + match-explanation), the conversational-query intent/preference model, a search/index over the product catalog, external-price API adapters and the timed refresh loop, plus the crowdsourced CRUD store with a moderation/verification pipeline. Languages: C++.
Backend scope: Local now, server-ready (T2) — Firebase for the crowdsourced DB; the Linux server seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the load-bearing piece is a performant C++ service — it parses the query (budget, product type, attributes), filters the catalog, compares candidates, ranks the best matches and decides when to ask a follow-up, plus a timed query loop that refreshes results/prices when data changes. This is genuine C++ information-retrieval work, not a database where clause or an external API call.
  • Data-driven: products, variants, attributes, retailers, stock/price entries, matching weights and the conversational intent schema are all hot-reloadable JSON — no hard-coded catalog or ranking constants.
  • 2D: the price-comparison / savings view is custom-rendered in OpenGL ES (retailer cards, stock badges, savings pills, a price bar) — the domain-adapted 2D surface (see adjustment 1). 3D: not needed. Networking: external retailer/price API calls + the crowdsourced-DB sync and (optional) push when a watched price changes.
  • Custom tool: the ImGui monitoring/testing console — change search parameters, trigger searches, view API responses, watch system performance and debug the backend (PC-side); it doubles as the moderation/verification review surface.
  • External DB: Firebase for the crowdsourced product/store/price database. Auth ⏭️: accounts for contributions and trust/attribution (safety-relevant for moderation). Analytics ⏭️: optional — which queries/products convert, to tune the ranker.

Track Goals & Team Composition

Team composition (set by instructor): 6 CS + 1 Design + 0 Art (7) — ScanIT is a UX-heavy utility app (scanner, conversational search + refine, the multi-store comparison sheet, the crowdsourced contribute/verify flows), and the visual surface (icons, store-logo placeholders, stock badges, savings pills) is UI-art the designer owns — there is no character/illustration production, so 0 artists (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). With 0 artists, the designer takes the D11 conditional as a real graded Design goal each milestone (M1 Art Proof of Concept / M2 Art Implementation Quality) — the last Design goal each milestone.
