Trippy (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Social Media · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A social travel platform that turns authentic user journeys into actionable itineraries. Instead of static POI databases or scraped reviews, Trippy builds its spatial dataset from verified traveller activity: as users map destinations, upload photos and categorize locations, a proprietary C++ engine infers dwell time, pacing, seasonality and spot popularity. Named technical features: an intent-based itinerary search engine (ranks complete multi-day itineraries against constraints, prioritising trips completed by social connections); a self-evolving spatial metadata pipeline (infers place metadata from minimal inputs); crowd-validated entity resolution (human-in-the-loop consensus for duplicate/offset entries via proximity prompts); and on-device instant itinerary optimization (a C++ engine reorders stops/day-clusters to a new user's pace/schedule/seasonality without network latency, streaming improved itineraries live). Custom tool: a C++ desktop editor sharing the engine — add places, seed starter itineraries, retune recommender weights and watch rankings re-sort, plus audio config; data-driven so behaviour changes without recompiling. Design features: collaborative trip planning (create/discover/plan-with-friends/shared itinerary); friend-sourced discovery (recommendations, save/organise, activity voting); travel details & tracking (document storage, day-by-day schedule, progress); and notifications/reminders (travel reminders, group updates, social-engagement alerts). Private post-trip collaborative hubs let groups compile photos and a shared scrapbook before itineraries are published to the community.

Adjustments required for approval:

  • Clear the 2D gate with a custom-rendered data-display surface. A native app built purely from a maps SDK plus native lists would collapse into ordinary CRUD and miss the module's 2D requirement. Custom-render at least one real 2D surface in OpenGL ES (GLSurfaceView) — e.g. the map with your own POI/route/popularity-heat drawing and the day-by-day itinerary timeline, and/or the editor's live "rankings re-sort" view — rather than only a drop-in map widget and RecyclerViews.
  • Privacy & moderation for the social/publish layer. Per-trip visibility (private hub vs friends vs published-to-community), report/block, and moderation of user photos/place data before public publish; don't expose precise personal/home locations. (Your private-hub model and per-trip control already point this way — make it an explicit, graded surface.)

(Not required, affirmed: the ranking/optimization/entity-resolution work is correctly scoped as the team's own load-bearing C++ engine — keep it that way. Map tiles/geocoding from a service are fine, but the scoring, re-ordering and dedupe stay in C++.)*

References:

  • Wanderlog (collaborative trip planner — create itineraries, discover, and plan trips together with friends)
  • Polarsteps (plan, track & relive trips — itinerary builder, route on a world map, photos, sharing, and full per-trip privacy control)
  • TripIt (all-in-one itinerary builder + trip planner with real-time flight alerts and travel reminders)

How each requirement applies:

Platform fit: Main: Native mobile — a native Android app (Kotlin UI + the C++ engine via JNI); the itinerary optimizer runs on-device (no network dependency) and the same C++ builds on the desktop for the editor/benchmarks (device: Pixel 9a). Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: The map (custom-drawn POIs, routes, popularity), the day-by-day itinerary timeline and drag-to-reorder planner, discovery/search results, the collaborative group hub, the shared scrapbook and trip-progress views (OpenGL ES for the custom map/timeline surface). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES) for the PC/desktop editor & benchmark build; Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The C++ engine — itinerary scoring/ranking against constraints (friend-weighted), on-device stop/cluster re-ordering with per-step re-scoring, the spatial-metadata inference pipeline (dwell/seasonality/popularity), and proximity-based entity resolution — plus a Firebase store for spatial data, social graph, groups and media, and a notification service. Languages: C++.
Backend scope: Local now, server-ready (T2) — the optimizer runs on-device; the Linux server seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the load-bearing piece is a performant C++ service — it scores hundreds of candidate itineraries against the traveller's taste, searches better orderings while re-scoring at each step, checks each new place against existing entries, and infers spatial metadata; it runs off the Kotlin UI thread over JNI and streams each improved itinerary to the screen. It has no Android/DB/UI dependency, so it also builds on the desktop for benchmarks and the regression suite.
  • Data-driven: places and inferred metadata, itineraries, recommender weights, seasonality vectors, entity-resolution radii and the notification rules are hot-reloadable JSON — the editor retunes engine behaviour without recompiling.
  • 2D: the map (own POI/route/popularity rendering), the day-by-day itinerary timeline and the editor's live re-sort view are custom-rendered in OpenGL ES (see adjustment 1). 3D: not needed. Networking: Firebase sync of the social graph/spatial data + push notifications (reminders, group updates, social-engagement alerts).
  • Custom tool: the C++ desktop editor sharing the engine — add places, seed starter itineraries, retune recommender weights and watch rankings re-sort live, plus audio configuration.
  • External DB: Firebase for spatial data, social graph, groups, media and logistics/documents. Auth ⏭️: accounts + friend graph. Analytics ⏭️: engagement events feed the spatial-metadata inference and stat views.
