Neighbour-Link - Team38 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Social Media · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): An application to revive local neighbourhood cohesion by matching residents through shared hobbies, proximity and community events. Rather than relying purely on remote servers, it uses an on-device C++ location and matching engine to process proximity and pair user profiles locally. To protect privacy and comply with PDPA, exact 6-digit postal codes are masked into 2-digit sector zones on-device before sync, allowing safe offline meetups without exposing home addresses. Four technical features: Anonymized Sector Geofencing (PDPA-compliant location processing), Smart Mutual Interest & Proximity Matcher, Live Location & Event Tracker, Instant Live Event Alerts & Sync. Custom tool: a Dynamic Hobby & Event Schema Editor (author hobby categories, matching criteria and event parameters with live in-app preview). Four design features: hobbies discovery feed, neighbourhood event creation tool, automated interest-matching feed, and a gamified reputation & local reward dashboard.

Adjustments required for approval: (the earlier blocker — that matching be the team's own load-bearing C++ service rather than a Firebase query — is now resolved by the on-device C++ engine; two minimal conditions remain)

  • Safety-by-design for connecting strangers offline. The sector-masking handles location privacy well; add the interpersonal safety surface too — verified accounts, report + block, per-user visibility controls, and a moderation / report-review dashboard (fold this into the custom tool), plus in-app public-place guidance for meetups. This is a graded surface, not an afterthought.
  • Rewards stay in-app points — no real money. Compute reputation/points server-side (anti-gaming) and keep the "local reward" as an in-app points ledger with redeemable codes; do not process real payments or run an e-commerce/discount-settlement flow, which would push the project into Fintech and out of scope for this trimester.

References:

  • Meetup — find local groups & events near you around shared interests
  • Bumble For Friends — match nearby people by shared interests, with photo verification and IRL meetups

How each requirement applies:

Platform fit: Main: Native mobile + Web browser on mobile — the on-device C++ location/matching engine, sector geofencing and push alerts are mobile-first (device sensors/GPS + on-device processing favour a native build), with a mobile-web front-end for reach; the Native PC build is the development/tools vehicle (device: Pixel 9a). Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: Hobbies-discovery feed, interest-match feed, event-creation and schema-editor screens, a live location/event proximity view (masked sector zones) and a reputation/reward dashboard (OpenGL ES for the custom feed cards, geofence/proximity view and reputation charts). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The on-device C++ engine (proximity/distance updates, on-device sector-masking, the user-matching state machine) plus a server tier for sync, notification dispatch, the reputation/points ledger and the moderation/report queue. Languages: C++.
Backend scope: Local now, server-ready (T2) — matching runs on-device; the Linux server seam is set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the load-bearing piece is the on-device C++ engine — a real-time update loop that ticks proximity/distance calculations, applies the PDPA sector-masking transform on-device (6-digit → 2-digit sector) before any sync, and drives the user-matching state machine (interest + masked-proximity scoring). This is genuine C++ systems work, not a database query.
  • Data-driven: hobbies, interest tags, matching criteria/weights, event parameters and reputation/reward tiers are all hot-reloadable JSON authored by the Schema Editor — no hard-coded hobbies, event types or scoring constants.
  • 2D: custom-rendered feed cards, a masked-sector proximity/geofence view, and reputation/engagement charts (custom-rendered, no chart libs) — the domain-adapted 2D surface for a Social Media app. 3D: not needed. Networking: Live Location & Event Tracker + Instant Live Event Alerts & Sync — push (FCM) + an in-app event bus + server sync of events and masked presence.
  • Custom tool: the Dynamic Hobby & Event Schema Editor (author hobby/tag/event schemas and matching criteria with live in-app preview), extended with a moderation / report-review dashboard (PC-side authoring/ops).
  • External DB: Firebase stores users, hobbies, events, the reputation ledger and reports (masked location only). Auth ⏭️: verified accounts are safety-critical here. Analytics ⏭️: optional engagement funnels — which hobbies/events convert to real-life meetups.
