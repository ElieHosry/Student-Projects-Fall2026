Neighbour-Link (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Social Media · Assessed: 2026-09-19 · Status: awaiting instructor approval

Proposal (as submitted): An application designed to revive lost community spirit by connecting neighbours who share common interests. Users are matched by location (postal code) and interest, can discover a hobbies feed, create neighbourhood events, and earn reputation and rewards (points redeemable for shop discounts). A C++ service continuously tracks and manages nearby users and events; a "Dynamic Hobby Creator" lets users define new hobbies. Named building blocks: location-based matching (postal code), database management, interest-matching algorithms, and a real-time notification system. Four major Design features: hobbies-discovery feed, neighbourhood event creation, interest matching, and reputation & reward.

Adjustments required for approval:

  • The interest + postal-code proximity matching must be the team's own load-bearing C++ service (a benchmarked ranking/matching engine with weighted scoring, not a Firebase query or a plain database where filter). The proposal already commits to "a C++ service that continuously tracks and manages nearby users and events" — hold the design to that; Firebase stays the store/sync layer, never the matcher (category guard-rail: Firebase alone must never be the backend).
  • Safety-by-design, because the product connects strangers to meet offline: verified accounts, report + block, per-user visibility controls, and a moderation / report-review dashboard (this is the custom tool) — plus in-app public-place guidance for event meetups. Treat this as a graded surface, not an afterthought.
  • Reputation and rewards computed server-side (anti-gaming) and the "shop discount" rewards must stay in-app points — a points ledger plus redeemable codes, not real payments or e-commerce. Real money would push the project into Fintech and out of scope for this trimester.

References:

  • Nextdoor — the neighbourhood network (verified neighbours, local events, shared-interest connections)
  • Meetup — find local groups & events near you around shared interests
  • Bumble For Friends — match nearby people by shared interests, with identity verification and IRL group plans

How each requirement applies:

Platform fit: Main: Native mobile + Web browser on mobile — location-based matching and push notifications are mobile-first (GPS/postal geocoding + FCM push favour a native build), with a mobile-web front-end for reach; the Native PC build is the development/iteration and tools vehicle (device: Pixel 9a). Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: Hobbies-discovery feed, nearby-neighbours / event proximity view, event-creation and hobby-creator screens, reputation/points display and notification centre (OpenGL ES for the custom feed cards, proximity map and reputation charts). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The C++ matching/tracking service (interest + postal-code proximity scoring, incremental re-ranking, nearby-users/events index), notification dispatch, reputation/points ledger and moderation/report queue. Languages: C++.
Backend scope: Local now, server-ready (T2) — the Linux server seam is set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the load-bearing piece is a performant C++ service that continuously maintains the nearby-users/events index and re-scores interest + postal-code proximity matches as users, hobbies and events change — weighted scoring and incremental re-ranking in C++, not a database query. Real-time notification dispatch runs off the same service.
  • Data-driven: hobbies (including user-authored ones from the Dynamic Hobby Creator), events, interest tags, matching weights, reputation rules and reward tiers are all hot-reloadable JSON — no hard-coded hobbies, event types or scoring constants.
  • 2D: custom-rendered feed cards, a nearby-neighbours / event proximity view, and reputation/engagement charts (custom-rendered, no chart libs) — the domain-adapted 2D surface for a Social Media app. 3D: not needed. Networking: real-time notifications (new nearby match, event invite, reputation change) and presence of nearby users/events via push + an in-app event bus.
  • Custom tool: the Dynamic Hobby Creator (author/curate hobby definitions and interest tags) plus a moderation / report-review dashboard (PC-side authoring/ops) — review the report queue, action blocks, and tune matching weights and reward tiers.
  • External DB: Firebase stores users, hobbies, events, reputation ledger and reports. Auth ⏭️: verified accounts are safety-critical here (identity/postal verification, report/block tied to identity). Analytics ⏭️: optional engagement funnels — which hobbies/events convert to real-life meetups.
