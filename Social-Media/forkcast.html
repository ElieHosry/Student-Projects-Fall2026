FORKCAST (student proposal)

Assessment: ✅ Fit · Category: Social Media · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Forkcast helps users and friend groups decide where to eat. A Dining Decision Bracket lets everyone swipe through restaurant options to narrow choices and break ties; the app compares everyone's picks into a final recommendation. As users visit restaurants, the app learns their Food Taste DNA; a Community Hub lets them find people with similar tastes (by preferences or Taste DNA), join cuisine communities, chat, and share reviews/discoveries. A Cuisine Tracker logs cuisines/restaurants tried and awards milestone badges shown off on the profile. Named load-bearing C++: the Bracket Simulation Engine — a live single-elimination state machine seeded from an integer + a restaurant-ID vector, swipe-driven, adding restaurants each swipe until a threshold/pick resolves; the Food Taste DNA performant service — a weighted vector/map (one dimension per cuisine tag) updated per dine-in with a decayed running average scaled by rating, with a weightage hierarchy (post-dine rating > repeat visits > dining-in-after-swiping > bookmarking > joining a hub > swiping); the Community Hub — TCP for chat text (server-relayed, buffered against overflow) and UDP with a sliding window for video/audio/image (chunked, missing-chunk detection + retransmit), event-driven high-throughput; and the Cuisine Tracker — Firebase Firestore (Users, Restaurants, Reviews, Leaderboards) with matching C++ data structures, a Linux-VM backend script pulling restaurants from the Google Places API and tagging cuisine/area into Firestore, C++-core review validation submitted through services to the backend, and backend cuisine-count + milestone-badge tracking. Team: 6 CS + 1 Design + 0 Art.

Note (category): Forkcast's core is social — cuisine communities, live chat + media, connecting people by Taste DNA, shared reviews, and show-off badge profiles — so it is assessed as Social Media; the bracket engine and Taste DNA are the decision/recommendation systems that feed the social network. (Runners-up considered: Visualization & Analytics for the Taste-DNA modelling, and a gamified-app lens for the badges.)

Note (module completeness): the design already leans on Firebase + a Linux VM backend + Google Places API — this is exactly the module's model (external DB mandatory; a Linux server set up by M2, full use T2). Platform: the swipe-first, on-the-go experience is a mobile app (Native Android, Pixel 9a). Scope caution: the UDP sliding-window media streaming (video/audio) in chat is genuinely hard — treat text chat as the floor and media as a stretch (see scope note).

References:

  • Beli — Wikipedia (a social app to track, rank and share restaurant experiences with friends, whose algorithm computes a "Match Score" to connect users with similar tastes and recommend places — the restaurant-tracking + taste-matching + social precedent, almost feature-for-feature)
  • Untappd — Wikipedia (a social check-in app where users log what they consume, earn milestone badges, and share to a community feed — the Cuisine-Tracker + badges + community precedent)
  • Tinder — Wikipedia (the origin of the swipe-through-a-stack-of-cards decision mechanic — swipe to like/dislike to narrow a set — the Dining Decision Bracket's swipe-UX precedent)

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 0 Art (8) — as proposed, and workable: a social/utility app's art surface is light-to-moderate (UI, the Taste-DNA visual language, the badge/icon set, profile styling), which the D11 conditional can carry — though the badge set is a real, reusable visual-asset job worth scoping deliberately. That said, a solo designer + 0 artists is the case the design pool flags ("must ask the instructor which conditional bends", see design-goals-pool.pdf), and the design load here is heavy — the group-decision UX, the Community-Hub social design, the recommendation/onboarding and the moderation/safety UX — so a 2nd designer is recommended (one owning the social/decision UX, the other the D11 visual surface + moderation UX). Scope note (advisory): the standout risk is networking breadth — a TCP chat relay is achievable, but a custom reliable-UDP sliding-window media stream (video/audio) is a research-grade task; make text chat + images the floor and treat live video/audio as a T2 stretch. Likewise, keep the Bracket + Taste DNA + Firebase tracker as the core M1/M2 spine, and let media streaming + advanced recommendations flex.
