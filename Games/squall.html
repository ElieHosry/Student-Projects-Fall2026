Squall (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Squall is a physics-based puzzle game where the instrument of manipulation is the player's fingers: players draw push, pull and time-freeze spells directly onto the screen as shapes to manipulate the world — jamming a mechanism with a box, yanking a key from across an inaccessible area, freezing objects to accelerate them toward a locked gate. Every puzzle has a goal but the solution is in the player's hands; three simple base spells let level architecture, systems and introduced mechanics carry the challenge. Named load-bearing C++: a stable rigid-body physics loop running many puzzle objects simultaneously; an ECS (contiguous memory for cache-efficient updates, decoupled rendering / physics / state-evaluation systems, transient event components + buffers for interaction handling); and a raycasted audio service casting dynamic sound rays for realistic acoustic occlusion + distance. Named technical features: vector/direction gesture recognition for drawn spells (real-time geometry + direction analysis distinguishing a circle from another shape); the dynamic physics system; the raycasted audio; and a level-streaming database for instant load (stream assets instead of loading all upfront). Tools: a level editor (free room layout — collision walls, spell/object-gated paths, room environment effects; entry/exit transition points) and a scriptable object system (transform/rotation/scale/ID-tag properties; typed objects like light sources, switches, buttons, pressure plates; custom script data for object-to-object interaction; reusable data assets placed many times). Design features: location-sensitive screen-drawing of spells; physics-based environmental interactions; the three spells — a circle that pulls surrounding objects, a triangle that freezes objects in time (accumulated forces/status effects all resolve on elapse), and a push that forces objects along/in front of it; and non-combative boss fights solved as puzzles using in-world objects. Team: 6 CS + 1 Design + 1 Art.

Note (module completeness): the proposal doesn't name a platform — the screen-drawn gesture spells are touch-first, so this is planned as a mobile build (Pixel 9a per the module). It also doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist level-completion / progress / settings there (a standard, small addition; see the External Database row + M1G12-style integration). Neither is a category concern.

References:

  • Crayon Physics Deluxe on Steam (a 2D physics puzzle where the player's drawings become real physical objects that solve the puzzle — the draw-a-shape-to-manipulate-physics precedent)
  • Ōkami — Celestial Brush (Ōkami Wiki) (the player pauses the world and draws shapes/strokes on screen, each recognised gesture triggering a distinct world-manipulation effect — the screen-drawn-gesture → recognised-effect precedent)
  • World of Goo on Steam (a physics-based puzzle where a small toolkit and level architecture — not raw power — create the challenge, and the player chooses the solution — the physics-puzzle-from-simple-rules precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — the screen-drawn spells are touch-first; a Web-on-mobile (Emscripten→WASM) build is a viable alternative. The Native PC build is the development/tools vehicle (the level editor + scriptable-object system). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for progress / level-completion persistence.
Front end: A 2D physics-puzzle renderer — the rooms, the many rigid-body objects (boxes, keys, gates, switches, pressure plates), the live gesture stroke the player draws, the three spell effects, and the puzzle/goal HUD. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The real-time C++ engine — the rigid-body physics loop over many puzzle objects, the ECS (contiguous storage, decoupled render/physics/state systems, transient event components), the real-time vector/direction gesture-recognition service, the raycasted audio service (occlusion + distance), and the level-streaming system; plus Firebase for progress persistence. Languages: C++ (engine + services); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the progress-persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: three load-bearing C++ pieces — the stable rigid-body physics loop (many simultaneous objects, the freeze-then-release-forces mechanic), the ECS (cache-efficient contiguous storage, decoupled systems, event buffers), and the raycasted audio service (dynamic sound rays for occlusion/distance); the gesture recognizer analyses stroke geometry + direction in real time to classify the spell.
  • Data-driven: object types + properties (transform/scale/ID, light sources, switches, buttons, pressure plates), the three spell definitions, room layouts, spell/object path-gates and environment effects are all data — a new object type or puzzle is a data change (authored via the editor + scriptable-object system).
  • 2D: the puzzle-room renderer, the live drawn-gesture stroke, the three spell VFX and the goal HUD (custom-rendered). 3D: not needed.
  • Custom tools: the level editor (room layout — collision walls, spell/object-gated paths, environment effects, entry/exit transitions) and the scriptable object system (typed, property-carrying, reusable data assets with object-to-object scripts).
  • Networking: single-player; progress persistence is async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵).
  • External DB: level-completion, progress and settings (Firebase — add this per the module). Auth ⏭️: optional accounts. Analytics ⏭️: optional — per-puzzle solve-time + spell usage for balancing.

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — as proposed, and well-matched: a physics-puzzle with a small object/spell vocabulary is a light-but-real art surface (readable puzzle objects, the three spell VFX, room environments, UI), which one artist can carry, while a single designer owns the puzzle/mechanic design, the level architecture and the spell-interaction systems (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the puzzle-content volume or the scriptable-systems design outgrows one designer, consider trading toward a 2nd designer. Scope note (advisory): a stable many-body physics loop + real-time gesture recognition + a raycasted-audio service + level streaming + a level editor + a scriptable-object system is a CS-heavy, ambitious scope — the three spells acting on a rigid-body room, gesture recognition for the three shapes, and a handful of hand-built puzzles is the M1/M2 floor; the raycasted audio, the streaming database, the full scriptable-object editor and the non-combative puzzle-bosses are the stretch. Recommend picking one of raycasted-audio or level-streaming as the M2 "hero" system if time is tight (both are genuinely optional-polish relative to the core physics+gesture loop).
