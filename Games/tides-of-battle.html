Tides of Battle (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Tides of Battle is a real-time, lane-based 1v1 strategy game built around faction deckbuilding. Players pick a primary faction (defining playstyle + unique cards) and build a deck from that faction alone or cross-faction for new synergies, then bring it into a real-time arena to deploy units, manage resources and react to the opponent. Three core pillars: resource management, strategic deckbuilding, reactive decision-making. Team: 6 CS + 1 Design + 1 Art. Named technical features: real-time multiplayer via deterministic lockstep (both clients simulate an identical world locally, exchanging only tiny command packets); fixed-timestep simulation decoupled from rendering; GPU-instanced sprite batching; and a data-driven content pipeline (units/cards share attributes — health, speed, range, faction). Load-bearing C++: two simulation loops in parallel — a client-side loop and a server-side service — both running the exact same simulation with only player inputs transmitted; an input-delay / frame-buffering system ties inputs to a simulation frame, and both clients only advance a frame once both inputs are available (guaranteeing a synchronized state); the server manages connections, receives inputs and distributes them. Tool: a network debugging tool (player connection status, ping, current frame, input + buffer; plus controls to simulate packet loss / lag to test the input-delay system). Design features: ≥3 factions (distinct playstyle/strengths/identity); ≥8 units per faction; a mana-based resource system; and cross-faction deckbuilding. (Monetization "can be integrated" via a gacha to unlock faction units.)

Note (monetization — design condition): unlocking gameplay units via gacha in a competitive 1v1 is pay-to-win, which breaks the module's clean-monetization rule. If monetization is added, keep all gameplay units earnable/free and restrict real-money purchases to cosmetics (no pay-for-power in ranked play). Owned by the M2 Design goal D8 if pursued.

Note (team/scope): 1 artist for 3 factions × 8 units = 24+ unit sprites (plus animations, UI and VFX) is a heavy load — scope the roster for the milestones (e.g. fewer units per faction at M1/M2, expand in T2), or consider adding a 2nd artist (the team has room to reach 9: 6 CS + 1 Design + 2 Art).

References:

  • Clash Royale — Wikipedia (the benchmark real-time 1v1 lane card battler: deploy units from an 8-card deck, a steadily-regenerating elixir/mana resource, arenas + trophy ranking — the real-time-lane + mana + deck + PvP precedent)
  • Warcraft Rumble — Blizzard (a real-time multi-lane collectible-unit battler with faction leaders/families, gold-based deployment and a rock-paper-scissors unit system — the real-time faction-army lane precedent)
  • Stormbound on Steam (a lane-based faction deckbuilding card battler — four kingdoms with distinct synergies, mana, and competitive PvP ladder — the faction-deckbuilding + cross-synergy precedent)

How each requirement applies:

Platform fit: Main: Native mobile (device: Pixel 9a) and/or Web browser on mobile — a real-time 1v1 card-strategy game suits either; the Native PC build is the development/tools vehicle (the network debug tool + the content editor). Extended: Firebase (accounts, collection, matchmaking/rating) + a Linux server the team sets up by M2 (full use T2) as the **lockstep relay** (manages connections, receives + distributes input packets).
Front end: A 2D renderer with **GPU-instanced sprite batching** for the many units/projectiles across the lanes, the deck/hand + mana HUD, the deckbuilder and collection screens — decoupled from the fixed-timestep sim. Languages: Native — Kotlin Native Android UI + C++ via JNI (Android Studio); Web — HTML/JS/CSS + C++→WASM (Emscripten); OpenGL ES sprite instancing in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The **deterministic fixed-timestep C++ simulation** (units, lanes, mana, combat) running identically on both clients, driven by lockstep input packets with frame-buffering; a **server-side loop/service** managing connections and relaying inputs; plus accounts/collection/rating. Languages: C++ (client sim + server relay); Firebase-backed services on the Extended tier.
Backend scope: Server-indicated (T2) — the lockstep relay + accounts/collection seam set up & basic-tested on the Linux host by M2, full use in T2.
  • Loop and/or service: the C++ loop is heavily load-bearing — a deterministic fixed-timestep simulation of units/lanes/mana/combat, decoupled from rendering, that advances a frame only once both players' inputs for that frame are buffered; the server-side service relays inputs. Determinism is the make-or-break property.
  • Data-driven: units/cards (health, speed, range, faction, abilities), the ≥3 factions and cross-faction rules, and mana costs are all data via the content pipeline — a new unit/faction is a data change.
  • 2D: GPU-instanced sprite rendering of the lane battlefield, units, projectiles and the deck/mana HUD (custom-rendered). 3D: not needed. Networking: ✅ the signature — real-time deterministic lockstep with input-delay/frame-buffering and a server relay (one of the few projects where a full real-time Networking System is central).
  • Custom tool: the network debugging tool (connection/ping/frame/input-buffer inspection + simulated packet-loss/lag) is excellent dev infrastructure; the team should also build a content-authoring editor (unit/card/faction editor on the data pipeline) as the graded content tool (see M2G2 ⭐).
  • External DB: accounts, the card collection, deck configs and matchmaking/rating. Auth ⏭️: accounts for ranked PvP. Analytics ⏭️: optional — faction/card win-rates for balancing.

Track Goals & Team Composition

Recommended composition: the team's stated 6 CS + 1 Design + 1 Art (8) is workable, but flag the art load: 3 factions × 8 units = 24+ unit sprites plus animations, UI and VFX is a lot for one artist. One designer owns the faction identities, the mana economy, the cross-faction deckbuilding and the competitive balance; the artist carries the faction unit rosters, the lane battlefield and the deck/collection UI. Recommendation: either scope the unit roster down for M1/M2 (fewer units per faction, expand in T2) or add a 2nd artist to reach 6 CS + 1 Design + 2 Art (9) (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). Scope note (advisory): deterministic lockstep + a deterministic sim + GPU-instancing + factions/deckbuilding + a content editor + matchmaking is a large surface — a deterministic 1-lane 1v1 with ~2 factions and a handful of units, the lockstep netcode and the content editor is the M1/M2 floor; all 3+ factions × 8 units, ranked matchmaking and the gacha (if any) are the stretch. Determinism across both clients is the single highest technical risk — prove it early (state-hash desync detection in M1).
