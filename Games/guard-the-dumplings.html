Guard the Dumplings - Team27 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Guard the Dumplings is a tower-defense strategy game in a European fantasy world where players defend a kingdom guarding an exclusive dumpling recipe from an enemy kingdom. Enemies invade in waves led by elite commanders and a final boss; players place tower units of different classes (Soldier, Archer, Mage) and spend an in-game currency, "dumpling mana" (earned from defeating enemies), to build and upgrade defenses. A day/night cycle structures play: battles occur only during the day (no building/upgrading), while night is the strategic phase for enhancing units and building towers. Named load-bearing C++: a game loop managing each wave — spawning many soldiers, updating towers, controlling projectiles at a stable step; a real-time AI pathfinding system continuously updating enemy and player soldiers' navigation toward goals; and a health system processing attacks/damage and updating HP + health bars in real time. Named technical features: a real-time enemy wave-spawning system; tower AI & targeting (auto-detect enemies in range, select targets by tower-specific behaviour); a grid-based placement + path-management system (validates placement, controls enemy movement along predefined paths); and adaptive AI pathfinding for enemy and player soldiers (navigate to the nearest target, adapting to the changing landscape). Tools: a custom map editor (which cells allow tower placement, which paths soldiers walk, and live editing of soldier/tower HP + game data); and a dev game-speed control (1×/2× to accelerate waves for testing wave progression, spawning and tower behaviour). Design features: the day/night cycle; tower upgrades across the three classes; progressive waves (regular troops → captain → King + elite boss stage); and the dumpling-mana economy (spend to upgrade or buy new tower types). Team: 6 CS + 1 Design + 1 Artist.

Note (module completeness): the proposal doesn't name a platform — a grid-placement TD is touch-friendly, so it's planned as a mobile build (Native Android, Pixel 9a). It also doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist progress / unlocked towers / level records there (a standard, small addition; see the External Database row + M1G12-style integration). Monetization: "dumpling mana" is an in-game, earn-by-play currency (clean); if real-money purchases are added, keep them cosmetic / non-pay-to-win per the module rule.

References:

  • Kingdom Rush — Tower Defense on Steam (the benchmark TD with Barracks (soldiers), Archer and Mage tower classes, waves led by bosses, and per-tower upgrades — an almost class-for-class match to the Soldier/Archer/Mage design)
  • Bloons TD 6 on Steam (place towers along predefined paths, earn currency from defeating enemies to buy and upgrade towers across branches, and survive escalating waves + boss bloons — the path-based + currency-to-upgrade + wave precedent)
  • Dungeon Defenders on Steam (a TD with an explicit build phase then combat phase — prep and place defenses, then fight the wave — the direct precedent for the night-build / day-battle cycle)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — grid placement + tapping is touch-first; a Web-on-mobile (Emscripten→WASM) build is a viable alternative. The Native PC build is the dev/tools vehicle (the map editor + the game-speed control). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for progress / unlock / level-record persistence.
Front end: A 2D top-down TD renderer — the grid map + paths, the three tower classes and their upgrades, the enemy troops/commanders/boss, projectiles, real-time health bars, and the day/night + dumpling-mana HUD. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; some screens (menus, upgrade shop) can be pure Native UI. Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The real-time C++ engine — the wave-spawning system, tower update + AI targeting, projectile control, the adaptive A* pathfinding for enemy + player soldiers, the health/damage system, the dumpling-mana economy and the day/night phase machine — holding a stable step with many soldiers on the mobile target; plus Firebase for progress persistence. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the progress-persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — per wave it spawns many soldiers, updates every tower's targeting + firing, advances projectiles, runs the adaptive pathfinding, and processes attacks/damage + health bars at a stable step, driving the day (battle) / night (build) phase machine.
  • Data-driven: the tower classes + upgrade tiers, enemy troops/commanders/boss, wave compositions, dumpling-mana costs and the map layouts are all data — a new tower, enemy or wave is a data change (authored in the map/data editor).
  • 2D: the grid map + paths, towers/troops/projectiles, real-time health bars and the mana/day-night HUD (custom-rendered). 3D: not needed.
  • Custom tools: two — the map editor (placement cells, soldier paths, live soldier/tower HP + game-data editing) and the dev game-speed control (1×/2× to accelerate waves for testing).
  • Networking: single-player; progress persistence is async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵). External DB: progress/unlocks/level records (Firebase — add per the module). Auth ⏭️ / Analytics ⏭️: module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — as proposed, and well-matched: a tower-defense has a contained but real art surface (three tower classes + upgrade tiers, the enemy roster of troops/commanders/King, the European-fantasy map, projectiles/VFX, UI) that one artist can carry, while a single designer owns the FDD, the level/wave design, the dumpling-mana economy + upgrade balance and the day/night structure (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the level/wave/balance content outgrows one designer, consider a 2nd designer. Scope note (advisory): a stable many-unit loop + adaptive pathfinding + tower targeting + a grid/path system + a map editor is a solid, well-understood TD scope — one map, the three tower classes, a few wave types with one commander, and the map editor is the M1/M2 floor; the full upgrade trees, the King-boss + elite commanders, multiple maps and the polished day/night economy are the stretch. Adaptive re-pathing (soldiers navigating a changing landscape) is the trickiest CS bit — validate it early on one map.
