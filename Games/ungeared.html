Ungeared (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Ungeared is a 2D dungeon crawler that inverts progression — instead of gaining gear, the hero loses it. Each floor cleared breaks a piece of equipment, and every loss changes how the run plays (when the lamp fails, the field of view shrinks, so the player must navigate the dark more carefully). Core loop: explore winding tunnels, scavenge potions left by fallen heroes, clear hordes of spiders, and push deeper as another piece of gear gives out. The cave doesn't change — the player's toolkit shrinks, forcing new tactics and decisions about when to spend saved potions; adaptation replaces raw power. Named load-bearing C++: a real-time simulation loop holding a stable step with ≥200 live spiders, via an ECS with contiguous component storage, a capped spawn system, pathfinding that only runs when a wall blocks the way, and batched rendering. Named technical features: a robust real-time spawning system; enemy AI & pathfinding (spiders crawl toward the hero by distance + line of sight, path resolved around walls); a seeded random map generator for paths + spawners; and a swipe-based combat system. Tools: seeded procedural level generation (specific seeds for a consistent experience across players); and an enemy-behaviour tuning tool (importer/exporter for speed, health, detection range, aggression — edit externally, import, export for balancing). Design features: the hero grows weaker, discarding equipment each stage; ≥3 "pictures-as-cutscene" depicting equipment failure; ≥3 wave-designed stages + 1 boss stage; and ≥3 spider types with distinct behaviours. Team: 6 CS + 2 Design + 0 Art.

Note (module completeness): the proposal doesn't name a platform — the swipe combat is touch-first, so this is planned as a mobile build (Pixel 9a per the module). It also doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist run records / seeds / best depth there (a standard, small addition; see the External Database row + M1G12-style integration). Neither is a category concern.

References:

  • Vampire Survivors on Steam (a horde-survival action roguelite where the screen fills with enemies and the player pushes to survive deeper — the hordes-of-enemies + ≥200-live-agents performance precedent)
  • The Binding of Isaac: Rebirth on Steam (a randomly-generated, run-based dungeon crawler where each run is a fresh combination of rooms and items — the run-based dungeon-crawler precedent)
  • Spelunky 2 on Steam (procedurally-generated caves from seeds, producing unique but reproducible descents each playthrough — the seeded-procedural-cave + "push deeper" precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — the swipe combat is touch-first; a Web-on-mobile (Emscripten→WASM) build is a viable alternative. The Native PC build is the development/tools vehicle (the enemy-behaviour tuning tool + the seed/level tooling). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for run records / seeds / best-depth persistence.
Front end: A 2D top-down dungeon renderer — the cave tunnels, the hero, up to ≥200 spiders (batched), potions/pickups, the shrinking field-of-view as the lamp fails, the equipment/potion HUD and the "pictures-as-cutscene" equipment-failure screens. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The real-time C++ simulation loop (ECS with contiguous storage, the capped spawning system, the wall-aware line-of-sight pathfinding that runs only when blocked, the equipment-degradation + potion economy, swipe-combat resolution and batched rendering), holding a stable step with ≥200 live spiders on Android; plus Firebase for run/seed persistence. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the run/seed-persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — the ECS + contiguous component storage, the capped spawn system, wall-aware LOS pathfinding computed only when a wall blocks, batched rendering and the per-floor equipment-degradation logic together hold a stable step with ≥200 live spiders on the mobile target.
  • Data-driven: spider types (≥3, with speed/health/detection-range/aggression), equipment pieces + their break-effects, potions, spawn tables, wave definitions and level seeds are all data — a new spider or gear effect is a data change (authored/tuned via the enemy-behaviour tool).
  • 2D: the top-down cave renderer, the batched spider horde, the shrinking-FOV lighting, the potion/gear HUD and the equipment-failure cutscene stills (custom-rendered). 3D: not needed.
  • Custom tools: two — the seeded procedural level generator (seeds → reproducible maps with paths + scattered spawners) and the enemy-behaviour tuning tool (import/export spider stats + AI params for external balancing).
  • Networking: single-player; run/seed persistence is async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵).
  • External DB: run records, seeds and best depth (Firebase — add this per the module). Auth ⏭️: optional accounts. Analytics ⏭️: optional — per-floor deaths + potion usage for balancing.
