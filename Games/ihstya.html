Ihstya - Team17 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Games · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Ihstya is a mobile lane-based deckbuilder defense strategy RPG (in the style of Arknights, Clash Royale and Counter:Side) where you enter battle with a fixed deck of Units and Artifice to fight off waves of enemies — using resource management to strategically summon heroes/soldiers and use artificery to defend your territory. Named load-bearing C++: a C++ Entity Component System decoupling data from execution to minimise memory fragmentation + pointer chasing; and a C# scripting layer for fast iteration + hot-reloadable data on top of the C++ native core (which handles the heavy logic). Named technical features: an entity logic state machine (moving/conflict); special rendering with entity culling; the ECS with C# scripting + hot-reloadable data; and an entity cone-detection system (field-of-view). Tools: a custom GUI editor (like Unity/Godot/Unreal) for debugging, editing + viewing data/scenes and live test-running UI + gameplay; and data serialization (JSON read optimally into the sim loop). Design features: Units (Named + Soldiers) with distinct attack patterns + skills/ultimates that interact dynamically (e.g. auto-counterattack when hit, or a teleport-behind-vision skill); lore-linked team synergies (units related by lore gain effects together — linked ultimates, stacking buffs by count on field); two decks with different functionality (an Artifice/Magic deck on cooldown where every card is always accessible, and a Summon/Unit deck on a shuffle where used units cycle back into the shuffle); and a dynamic map that magic + units interact with (spells summon walls that block pathing forcing detours, or build a temporary portal/bridge to bypass terrain). Team: 6 CS + 2 Designers + 1 Artist.

Adjustments required (why 🔶):
  1. Monetization — the "gacha" model must be non-pay-to-win. The module's clean-monetization rule forbids pay-to-win: real-money purchases must be cosmetic-only. A gacha that sells gameplay-affecting Units for real money is pay-to-win and is not permitted. Keep unit acquisition earned by play (in-game currency only), or restrict any real-money purchases to cosmetics — and design this explicitly (see the M2 Monetization & Scope-Integrity design goal). This is a design-model change, not a tech blocker.
  2. The C# scripting layer is an ambitious, non-required extra — keep the C++ core load-bearing. The module is built around a C++ core + data-driven JSON hot-reload (which already gives you fast iteration without recompiling). Embedding a C# scripting runtime (Mono/.NET) on top adds real toolchain + interop complexity and is not required. Treat C# scripting as a stretch: deliver the required computational logic in C++ with JSON hot-reload first; add a scripting layer only if time allows, and ensure the graded C++ engine carries the load-bearing logic regardless.
The core game (lane deckbuilder defense, ECS, two-deck systems, dynamic map) is a strong, well-scoped Games fit once these two are settled.

Note (module completeness): the app needs an External Database (unit rosters / collection / accounts) — use Firebase and/or the team's Linux server (set the seam up + basic-test it by M2). Platform: Arknights/Clash-Royale-style → a mobile build (Native Android, Pixel 9a).

How each requirement applies:

Front end: A 2D lane-battle renderer — the many units (heroes/soldiers) with culling, the two decks (cooldown Artifice + shuffle Summon), skill/ultimate VFX, the dynamic map (walls/portals/bridges), and the resource/HUD. Back end: The real-time C++ engine — the ECS (contiguous storage, low fragmentation), the entity state machine (moving/conflict), unit skills/ultimates + lore synergies, the two-deck economy (cooldown + shuffle), the entity cone-detection, the dynamic-map pathing, and special rendering with culling — driven by JSON hot-reload (and, as a stretch, a C# scripting layer); plus Firebase for accounts/collection. Languages: C++ (native core — load-bearing); optional C# scripting layer; Firebase on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts/collection seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ ECS loop is the heart — it runs the entity state machine, unit skills/ultimates + synergy resolution, the two-deck economy, cone-detection and the dynamic-map pathing at a stable step, with data hot-reloaded from JSON (the C++ core carries the heavy logic; C# scripting is an optional layer, not the graded core).
  • Data-driven: units (heroes/soldiers) + skills/ultimates, lore-synergy rules, the two decks, artifice/magic effects and the dynamic-map spells are all data — a new unit, skill or spell is a data change (authored in the editor, JSON-serialized).

  • Custom tool: the custom GUI editor (Unity/Godot/Unreal-like) — debug, edit + view data/scenes, and live test-run UI + gameplay — plus the JSON serialization pipeline.
  • Networking: single-player PvE lane defense as described (no real-time PvP), so a Networking System is optional (🔵). External DB: accounts + unit collection (Firebase — add per the module). Auth ⏭️ / Analytics ⏭️: module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 2 Design + 1 Art (9) — as proposed, and sensible for a systems-deep game: two designers can split the heavy design load (the two-deck economy + synergies, the unit/skill/ultimate design, the dynamic-map + wave design, the balance, and — importantly — the monetization/scope-integrity design the 🔶 adjustment requires), while one artist carries the visual surface. Note this is at the D + A ≤ 3 cap (2 Design + 1 Art), so a 2nd artist can't be added without dropping a designer. Art-scope caution: a collection/gacha-style RPG is art-heavy (many Named units, skills/ultimates VFX) but has only one artist — scope the Named-unit roster small (a handful of distinct heroes + reusable soldier/enemy art), lean on a strong reusable style, and let the ambitious roster be a T2 stretch. Scope note (advisory): a C++ ECS + entity state machine + cone-detection + dynamic-map pathing + the two-deck systems + a Unity-like editor is a large, ambitious CS scope even before the C# scripting layer — the ECS lane battle with the two decks, a few units with skills, the dynamic-map walls, and the editor's core is the M1/M2 floor; the C# scripting layer, the full synergy/linked-ultimate web, cone-detection-driven AI and the live test-run editor are the stretch. Settle the monetization model early (it changes the collection/economy design) and keep the C++ core load-bearing (C# is optional).
