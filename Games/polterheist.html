Polterheist - Team34 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A mobile perspective-switching puzzle game (in the vein of Toodee and Topdee). You play a kleptomaniac ghost robbing the underworld: the main body is controlled in a side-view (tap to move toward a point), while the "spirit" sees the world in a top-down ¾ view, flies undetected, and possesses blocks to move them around. Get the body to the target without detection to complete the heist. Named technical features: side-view ↔︎ top-down isometric perspective switching (player controls the viewing angle); a data-driven engine tailored to designer needs; a server-side solution for leaderboards and social functions; procedural map generation from preset sections. Custom tools: a game editor, runtime debug tools, and a custom map/room editor for the procedural generation. Design features: the perspective-switching mechanic (reshape the stage from the top-down view); ≥5 possessable block types with unique stage interactions; ≥5 designed stages using the perspective/gravity switch; ≥3 enemies with distinct behaviours. Target 16 ms frametime.

References:

  • Toodee and Topdee on Steam (the stated inspiration — a 2D-platformer × top-down-puzzler hybrid; switch perspectives, and the world bends to the current genre's rules)
  • FEZ — Wikipedia (perspective-shifting 2D/3D puzzle-platformer built on rotating between orthogonal views)
  • Monaco: What's Yours Is Mine on Steam (top-down stealth heist — case the joint and steal without detection, with leaderboards and a level editor)

How each requirement applies:

Platform fit: Main: Native mobile + Web browser on mobile — tap-to-move and tap-to-possess are touch-first and the ¾ top-down/side switch suits a phone screen (device: Pixel 9a); the Native PC build is the development/tools vehicle. Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: Dual renderer — a side-view of the body and an isometric ¾ top-down view of the spirit and the level — with the perspective-switch transition, possessed-block highlighting, detection/stealth cues and stage HUD (OpenGL ES). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: Engine core (fixed + variable timestep loop targeting 16 ms, entity system, per-perspective physics/collision & gravity, block-possession system, enemy AI & detection, procedural room assembler) + a leaderboard/social service. Languages: C++.
Backend scope: Local now, server-ready (T2) — leaderboard/social seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — it advances the body (side-view movement to a tapped point), the spirit (free top-down flight + block possession/movement), per-perspective physics and gravity, enemy behaviour and detection, and the perspective-switch state, holding a 16 ms frame budget with mixed fixed/variable timesteps.
  • Data-driven: stages, the ≥5 block types and their interactions, the ≥3 enemies and their behaviours, preset rooms for procedural generation and the perspective/gravity rules are all hot-reloadable JSON authored via the editors — a data-driven engine tailored to the designers.
  • 2D: sprite/tile rendering of both the side-view and the isometric ¾ top-down view, the switch transition, possession and detection VFX (custom-rendered). 3D: not needed (the ¾ view is 2D/iso sprites). Networking: async leaderboards / social via Firebase; no real-time netcode.
  • Custom tool: a game editor + a custom map/room editor (author preset rooms for procedural assembly, place blocks, spawns, targets and detection zones) with live preview, plus runtime debug tools.
  • External DB: leaderboards and social functions. Auth ⏭️: accounts for leaderboards/social. Analytics ⏭️: optional — where players are detected/stuck, for stage balancing.

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 2 Art (9) — every block, room and enemy needs art in two projections (a side view and an isometric ¾ top-down view), so the environment/character art roughly doubles and earns 2 artists; a solo designer owns the perspective/gravity/possession puzzle design across the ≥5 stages and the block-interaction matrix (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If stage/puzzle volume outgrows one designer, trade the 2nd artist for a 2nd designer. Scope note (advisory): perspective switch + gravity + ≥5 blocks + ≥5 stages + ≥3 enemies + procgen + editor + server is a large surface — treat the perspective-switch + possession core with 2–3 hand-built stages and the editor as the M1/M2 floor, with procedural assembly and the server layer as the stretch.
