Framebreak - Team20 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): You are a prisoner escaping with a magical camera: snapping a real-world object materializes a functional 3D item inside your cell to overcome obstacles. Camera power is limited, so every snapshot demands observation and spatial strategy — scout your surroundings, pick the best item, capture it to solve each area's escape puzzle. Named technical features: (1) time-zone-synchronized procedural level generation; (2) an AI photo→3D pipeline — a photo is classified to identify the object and assign gameplay attributes, sent to the backend where the background is stripped and an image-to-3D model generates a textured mesh, which a C++ service reduces and fits with collision shapes before it streams back and spawns, with a progress/status indicator; (3) real-time 3D co-op multiplayer; (4) an attribute-matching puzzle system that checks a spawned object's properties against a room's exit requirements (any item with the right attributes solves it). Loop/service: a C++ backend service turns the raw generated mesh into something the phone can use — mesh reduction, texture bake, collision generation; since every photo is unique nothing is reusable, so the service's throughput decides how many concurrent players are supported. Tools: a desktop room editor on the same C++ renderer (place geometry, set each room's exit requirement as an attribute list, set the camera charge limit); a server hosting the image-to-3D app (device sends photo → server returns a 3D model → used in the loop). Design features: photo-to-object manifestation; a cooperative escape mode (solo or online co-op, combine snapshots to solve complex puzzles); dynamic time-of-day puzzles (layouts change for morning/afternoon/evening/midnight); and a hybrid monetization system (base 10 snaps/area, a "large battery pack" raises it to 20; paid hints).

Why "with adjustments" (conditions for week-5 approval):

  1. Keep the load-bearing C++ on the team's side of the AI. The module's performant-C++ requirement is met by your mesh-processing service (decimation, texture bake, collision-shape generation, streaming) + the game loop + the attribute-matching puzzle system + procedural generation — not by calling an external image-to-3D ML model. Treat the ML image-to-3D as one bounded component behind the service interface, and build a fallback (a curated library of pre-made meshes keyed by the classifier) so the game is fully demoable at the showcase even if the ML pipeline's latency or quality falls short. The classifier/image-to-3D itself is not a graded CS goal; the C++ service around it is.
  2. Rework the monetization. Selling extra snaps (10 → 20 via the battery pack) and paid hints is pay-for-advantage, which breaks the module's clean-monetization rule (no pay-to-win, no manipulative loops). Make the snap budget a balance/earned decision and hints free or earned, and restrict any real-money purchases to cosmetics. (Design goal D8 in M2 owns this.)
  3. This is a genuine 3D project (image-to-3D meshes, 3D items, 3D co-op) — the "3D (strong students only)" row applies, and it is the central technical risk. Scope the floor to single-player with a curated object set and a few rooms (the mesh service + attribute puzzle proven), with the ML photo→3D, real-time co-op and time-of-day generation as the stretch.

References:

  • Viewfinder on Steam (a first-person puzzle game whose core verb is turning photographs into real 3D geometry you place into the world to solve puzzles, with a limited-film camera — the closest precedent for photo→3D-object manifestation under a snap budget)
  • Escape Simulator on Steam (first-person escape-room puzzles playable solo or in online co-op, with a room editor and community rooms — the co-op-escape + room-editor precedent)
  • Scribblenauts — Wikipedia (summon almost any object, whose attributes interact with the level to solve a puzzle — the "any item with the right attributes solves it" precedent)

Languages: C++ (loop + service).
Backend scope: Server-indicated (T2) — the image-to-3D + mesh service + accounts seam set up & basic-tested on the Linux host by M2, full use in T2 (the service's throughput sets the concurrent-player ceiling).
  • Loop and/or service: two load-bearing pieces — the client fixed-timestep loop (spawned-object physics/collision, attribute-puzzle evaluation, time-of-day layout) and the C++ performant service that turns each unique generated mesh into a phone-ready asset (decimate → bake → collision → stream); its throughput decides concurrent players (measured in M1G3 / M2G1).

Networking: real-time 3D co-op (authoritative state, sync spawned objects across players).

  • External DB: accounts, progression and the (reworked, cosmetic-only) store. Auth ⏭️: accounts for co-op + store. Analytics ⏭️: optional — which objects players snap, where they get stuck.

Track Goals & Team Composition
