Dash Party - Team22 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A retro-arcade party game about race cars, with four game modes (and room to expand) — from classic racing to obstacle courses where two players share control of one car — bringing fast-paced race-car chaos to couch/party play with friends. Named technical features: private-room multiplayer; a dual-to-quad split screen; a server-side solution for a global database and account registration; a mobile controller driven by the phone's gyroscope sensors. Named CS features: mini C++ game loops accepting multiple real-time network connections from mobile devices through the browser; a custom editor to author and import new minigames to grow the mode roster. Design features: 4 game modes, each with its own race courses; a roster of 3 car types; 4 controller layouts (one per mode); 3 unlockable skins per car type (via in-game currency or in-app purchase).

References:

  • The Jackbox Party Pack on Steam (the phone-as-controller party model — players join at a jackbox.tv web address and their phones/tablets become the controllers; the precedent for Dash Party's browser-connected gyro controllers)
  • Horizon Chase Turbo — Aquiris (a modern retro-arcade racer explicitly inspired by Out Run / Top Gear / Rush, with a split-screen multiplayer mode — the aesthetic + split-screen precedent)
  • Micro Machines — Wikipedia (top-down miniature-car party racing built around shared-screen local multiplayer — the couch-chaos party-racer precedent)

How each requirement applies:

Platform fit: Main: Web browser on mobile — the game client runs in the browser (a phone, tablet or a laptop/TV acting as the shared "party screen"), and each player's phone joins as a gyroscope controller through the browser (DeviceOrientation), so no app install is needed; the Native PC build is the development/tools vehicle. Extended: Firebase + a Linux server the team sets up by M2 (full use T2) hosting the private-room matchmaking/relay and the global account database.
Front end: A retro-arcade 2D renderer with a dynamic dual-to-quad split screen (1–4 viewports for 1–4 local racers), each drawing its car, the course, obstacles and HUD; plus the phone-controller web page (a gyroscope steering surface + buttons) and the lobby/room-code screens. Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); the phone-controller page is HTML/JS reading the DeviceOrientation API.
Back end: The C++ engine core (fixed-timestep race loop, car handling & collision physics, obstacle logic, the 4 mode rulesets, the dual-control resolver, split-screen cameras) + a private-room networking layer that accepts many real-time phone-controller connections through the browser, plus a global-account/leaderboard service. Languages: C++ (engine); the relay/matchmaking service on the Linux server.
Backend scope: Local now, server-ready (T2) — private-room relay & global-account DB seam set up & basic-tested on the Linux server by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — it advances every car's handling and collisions, obstacle and course logic, the four mode rulesets, the two-players-one-car control resolver, and the split-screen camera state at a fixed timestep while ingesting live input from the connected phone controllers. The proposal's "mini C++ game loops accepting multiple real-time network connections through the browser" is exactly this requirement.
  • Data-driven: the 4 game modes and their rules, each mode's courses and obstacle layouts, the 3 car types and their handling stats, the 4 controller layouts, and the skin/currency definitions are hot-reloadable JSON authored via the minigame editor — this is what lets new modes be imported without a recompile.
  • 2D: retro-arcade sprite/tile rendering of cars, courses, obstacles and HUD, drawn into a dual-to-quad split screen (dynamic viewport layout for 1–4 local players) — custom-rendered. 3D: not needed (the arcade look is 2D sprites). Networking: private-room multiplayer + many concurrent phone-controller connections (real-time input) + async global leaderboards.
  • Custom tool: the minigame editor — author a new mode's ruleset, course/obstacle layout and controller mapping as data, preview it, and import it to grow the roster beyond the launch four.
  • External DB: the global account database + per-car skin ownership and leaderboards. Auth ⏭️: account registration. Analytics ⏭️: optional — per-mode play counts and drop-off, for balancing.

Track Goals & Team Composition

Recommended composition: 6 CS + 2 Design + 1 Art (9) — the design surface is unusually large for a party title (4 distinct game modes each with its own ruleset and courses, 4 controller layouts, the two-players-one-car mechanic, and the skin/currency economy), so two designers split the mode/level/systems design and the UI/UX across the shared-screen HUD and the phone-controller pages; a single artist can carry a cohesive retro-arcade pixel style (3 car types + their skins as palette/variant sets, four modest course/obstacle sets, and the arcade UI) — small, palette-driven sprites keep the volume tractable for one (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the four modes' art volume outgrows one artist, trade the stretch scope, not the headcount. Scope note (advisory): four modes + dual-control + split-screen + private-room netcode + phone controllers + editor + server is a very large surface — treat the classic-race mode with 2–4 local players (split screen), the phone-controller transport and the editor as the M1/M2 floor, with the extra modes, online private rooms and the leaderboard server as the stretch.
