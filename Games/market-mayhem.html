Market Mayhem - Team23 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Market Mayhem is a 2D top-down single-player combat racing game. The player is in a supermarket with a grocery list and a trolley, travelling around to collect the listed items; whoever completes their list and reaches the cashier first wins. The player and 3 NPCs can crash into one another to knock items to the floor, steal them, and immobilise each other temporarily; each item (including grocery-list items) has different effects to boost the player or sabotage others. Named load-bearing C++: a game loop holding a stable step with multiple shoppers each with their own AI, inventories, physics and values (speed, acceleration, heat gauges, etc.), running deterministically. Named technical features: Enemy AI & Pathfinding (other shoppers collect items they need or crash into the player while avoiding walls); a real-time physics engine handling multiple shoppers moving + crashing; movement physics mimicking vehicle controls (joystick, gear shifting, drifting); and item effects affecting runtime logic (many items, each with its own effect). Tool: a modular effect system — a reusable framework (e.g. a custom effects editor) to handle the real-time logic for item effects. Design features: trolleys with acceleration/braking/crashing; items with special effects; the supermarket + item aisles to collect from; and grocery lists that track collected items. Team: 6 CS + 1 Design + 1 Artist.

Note (module completeness): the proposal doesn't name a platform — the joystick/vehicle controls are touch-friendly, so it's planned as a mobile build (Native Android, Pixel 9a; a Web-on-mobile build is a viable alternative). It also doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist progress / high scores / unlocks there (a standard, small addition; see the External Database row + M1G12-style integration). Neither is a category concern.

References:

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — joystick + gear/drift controls are touch-first; a Web-on-mobile (Emscripten→WASM) build is a viable alternative. The Native PC build is the dev/tools vehicle (the custom effects editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for progress / high-score / unlock persistence.
Front end: A 2D top-down renderer — the supermarket + aisles, the player + 3 NPC trolleys, the items, crash/effect VFX, and the grocery-list + heat-gauge/effect HUD. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; some screens (menus) can be pure Native UI. Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The deterministic real-time C++ engine — the fixed-timestep loop over the player + 3 NPC shoppers (each with AI, inventory, physics + values like speed/acceleration/heat), the vehicle movement + crash physics, the enemy AI + wall-avoiding pathfinding, and the modular item-effect system driving runtime logic — plus Firebase for progress/scores. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the progress/score seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the deterministic C++ loop is the heart — it advances four shoppers (each with AI, inventory, physics + heat/speed values), resolves trolley movement + crashes, and applies item effects to the runtime logic at a stable step.
  • Data-driven: the item catalogue + their effects, the grocery lists, the supermarket layout/aisles and shopper stats (speed/accel/heat) are all data — a new item, effect or list is a data change (authored in the effects editor).
  • 2D: the top-down supermarket renderer, trolleys, items, crash/effect VFX and the grocery/heat HUD (custom-rendered). 3D: not needed.
  • Custom tool: the modular effect system / custom effects editor — author and wire item effects (boost/sabotage/steal/immobilise) as reusable, data-driven modules without hard-coding each in the engine.
  • Networking: single-player (player vs 3 AI), so a Networking System is optional (🔵). External DB: progress/high-scores/unlocks (Firebase — add per the module). Auth ⏭️ / Analytics ⏭️: module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — as proposed, and well-matched: a top-down combat racer has a contained but real art surface (the supermarket + aisles, the 4 trolleys/shoppers, the item icons, crash/effect VFX, UI) that one artist can carry, while a single designer owns the FDD, the vehicle game-feel, the item-effect catalogue + boost/sabotage balance and the AI difficulty (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the item/effect content outgrows one designer, consider a 2nd designer. Scope note (advisory): a deterministic 4-shopper loop + vehicle/crash physics + wall-avoiding AI + a modular effect system is a solid, well-contained single-player scope — the trolley handling + crashing, 2-3 items with effects, one supermarket and basic NPC AI is the M1/M2 floor; the full item roster, the smart per-shopper AI tactics and the polished effects editor are the stretch. The modular effect system is the smartest lever — it lets the team add items as data rather than engineering each; get its architecture right early.
