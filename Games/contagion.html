ConTagion - Team14 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A 2D, introspective, story-based survival platformer set in the ruins of a city trapped 10,000 feet underground after an apocalyptic earthquake. The player navigates out with the help of a pet dog — the only one able to sense safe routes — avoiding unstable structures, falling debris, aftershocks, cannibalistic humans and infected creatures, across at least 5 levels with 4 different endings. Named technical features: gyro-based environment control for hazards/traps; player movement + pet command + collision; dog AI pathfinding + threat detection; enemy AI (idle/chase/attack) for player and dog. Custom tools: a scene/tile-map editor (falling structures, hazards like exposed wiring and fire), an enemy controller (spawn/detection/attack range), a player & dog controller, an obstacle trigger (aftershocks, cave-ins, enemies) and inventory/resource configuration. A server-side service stores inventory, level and completion time.

References:

  • Never Alone (Kisima Inŋitchuŋa) — Wikipedia (atmospheric 2D puzzle-platformer; swap between a girl and her Arctic-fox companion to clear hazards)
  • Little Nightmares — Wikipedia (2D survival-horror puzzle-platformer; a child evades grotesque/carnivorous enemies with only a lighter)
  • INSIDE — Wikipedia (Playdead's dark 2D survival-platformer; evade pursuers and hazards, with a hidden alternate ending)

How each requirement applies:

Platform fit: Main: Native mobile + Web browser on mobile — the gyro/tilt hazard control and touch controls are mobile-first (the device gyroscope favours a native build), with a mobile-web front-end for reach; the Native PC build is the development/tools vehicle (device: Pixel 9a). Extended: Firebase + Linux server set up by M2 (full use T2).
Front end: Side-scrolling level renderer (player, dog, enemies, hazards, debris), lighting/atmosphere for the dark ruins, HUD (health/stamina, inventory, dog-command state), and menus/ending screens (OpenGL ES). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: Engine core (fixed-timestep loop, entity system, platformer physics & collision, hazard/aftershock simulation, dog AI pathfinding + threat detection, enemy AI state machines, inventory/resource systems) + a save/progress service. Languages: C++.
Backend scope: Local now, server-ready (T2) — save/inventory/completion-time seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the fixed-timestep C++ loop is load-bearing — it steps player movement (run/jump/climb) and stamina, the dog's pathfinding and threat detection, enemy AI (idle/chase/attack) against both player and dog, hazard/aftershock triggers (falling debris, cave-ins, fire, flooding) and collision resolution, plus the gyro input that tilts/destabilises structures, all in real time.
  • Data-driven: levels/tile maps, hazards and triggers, the two enemy types and their behaviour parameters, the dog's command set, survival resources/items and the 4 ending conditions are all defined as hot-reloadable JSON — no hard-coded levels, enemies or hazards.
  • 2D: side-scrolling sprite/tile rendering of the ruined city, player, dog, enemies, debris and hazard VFX, with atmospheric lighting (custom-rendered). 3D: not needed. Networking: optional — cloud save/leaderboard only; no real-time netcode.
  • Custom tool: a scene / tile-map / hazard editor (place tiles, falling structures, exposed wiring, fire, spawn points and aftershock/cave-in triggers; set player/dog spawns; configure enemy spawn/detection/attack ranges; author inventory/resources) with live preview.
  • External DB: server-side inventory, level reached and completion time. Auth ⏭️: optional accounts. Analytics ⏭️: death/failure funnels — which hazard, enemy and level the run ends on, for balancing.

Track Goals & Team Composition

Team composition (set by instructor): 6 CS + 1 Design + 0 Art (7) — a story-driven survival platformer with a player, a dog companion, two enemy types, a ruined-city environment across 5 levels and heavy hazard/animation/VFX demand is a large character + environment + animation art surface that now has no artist, so the single designer owns the survival loop, level/puzzle design and the 4-ending narrative and takes the D11 conditional as a real graded Design goal each milestone (M1 Art Proof of Concept / M2 Art Implementation Quality — the last Design goal each milestone), which consumes one Design+UI slot per milestone (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). Art-risk flag: this is a very art- and animation-forward game (character roster + ruined-city environment + hazard/VFX + the 4 ending cutscenes), so 0 artists is a serious risk — scope levels/roster hard and lean on a reusable silhouette-first style under D11, or reconsider adding an artist within the D+A ≤ 3 cap (a solo designer + 0 artists is the case the design pool flags, and squeezes the designer's systems/balance goals). Scope note (advisory): 5 levels × 4 endings × 2 enemy types is ambitious — treat 2–3 polished levels + the 4 ending hooks as the M2 showcase floor and let the editor scale content afterward.
