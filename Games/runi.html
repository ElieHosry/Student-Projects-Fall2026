Runi (student proposal)

Assessment: ✅ Fit · Category: Games (gamified-app lens) · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Runi is a gamified running platform that turns real-world running into an interactive experience with challenges, progression, achievements and social interaction to build consistent habits. Named load-bearing C++ (the Runi Activity Engine): a subsystem that processes incoming GPS samples, filters noisy readings, calculates distance and pace, tracks route progress, interpolates ghost positions and generates real-time race events (distance-milestone reached, personal-best split beaten, ghost overtaken, challenge objective completed). Named technical features: GPS Route Tracking & Ghost Racing (race a "ghost" of your previous/personal-best run or a friend's, with live ahead/behind stats on completed routes); Virtual Pet Progression & Reward (a persistent pet whose XP/accessories/cosmetics are driven by streaks, distance milestones, specific routes and challenges); Social Network & Competitive Leaderboards (friends, shared activities, challenges, leaderboards by route-time/distance/achievements); and an Achievement & Challenge System (configurable objectives → XP/achievements/cosmetics). Tools: a content-authoring tool (configure challenges, achievements, progression values, cosmetics and rewards as data, distributed via the backend — a data-driven workflow); and a testing tool that simulates running activity (GPS movement, distance, pace, completed runs) so developers can test/debug/balance ghost racing, challenges, rewards and pet progression without physically running, with adjustable speed/distance/progression. Design features: a Running Dashboard, an Adaptive Goal System, Friends & Community, a Challenge Hub, Personal Racing (live ahead/behind), a Virtual Pet & Profile (raise/customise/equip cosmetics), and Pet Activity States (happy/energetic/sleepy/exhausted; hatch + evolve on milestones). Team: 6 CS + 1 Design + 0 Art.

Note (category): like other gamified apps (there is no fitness/health category), Runi is filed under Games and assessed through the gamified-app lens (session/progression/retention systems) — the same way the module treats step-and-pet and habit-loop projects. (A Social Media reading was considered for the friends/leaderboard layer, but the core is the gamified running/pet loop.)

Note (module completeness): Runi needs a backend + external DB (persistent pet/XP/cosmetics, runs, leaderboards, social graph, content packs) — use Firebase and/or the team's Linux server (set the seam up + basic-test it by M2). Platform: GPS + on-the-go use → a mobile build (Native Android, Pixel 9a). Monetization: none specified and the economy is earn-by-running (XP/cosmetics), which is clean; if real-money purchases are added, keep them cosmetic / non-pay-to-win per the module rule.

References:

  • Strava — Wikipedia (the benchmark GPS running/cycling app with route + pace tracking, segment leaderboards and a social feed where users follow each other and compete on segment times — the GPS-tracking + social + leaderboard + segment-racing precedent)
  • Tamagotchi — Wikipedia (the archetypal virtual pet you raise and customise, whose states and branching evolution depend on how it's cared for — the persistent-pet + activity-driven-states + hatch/evolve precedent)
  • TrackMania — Wikipedia (the racing benchmark for ghost racing: race against a recorded ghost of your best time or others' times, submitted to online leaderboards — the ghost-of-a-previous-run + live-comparison precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ Activity Engine via JNI, OpenGL ES for the map/ghost/pet rendering in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — GPS, background-safe run recording and on-device state are native concerns. The Native PC build is the dev/tools vehicle (the content-authoring tool + the GPS-simulation testing tool). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for pet/XP/cosmetic persistence, runs, leaderboards, the social graph and content-pack distribution.
Front end: A 2D app — the Running Dashboard, the route map with the live ghost + ahead/behind feedback, the Challenge Hub, leaderboards/friends feed, and the virtual pet (states, cosmetics, evolution). Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime map/ghost/pet in a GLSurfaceView; dashboard/social/profile screens can be pure Native UI. Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The C++ Runi Activity Engine — GPS ingest + noise filtering, distance/pace, route-progress tracking, ghost-position interpolation and real-time race-event generation — plus the pet-progression, achievement/challenge and leaderboard systems; a backend (Firebase/Linux server) for persistence, social and content packs. Languages: C++ (engine); Firebase/server on the Extended tier.
Backend scope: Local now, server-backed (T2) — the persistence/social/content seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ Activity Engine is the heart — per GPS sample it filters noise, updates distance/pace + route progress, interpolates the ghost, and fires race events (milestone, PB split, ghost overtaken, challenge complete).
  • Data-driven: challenges, achievements, progression curves, cosmetics, rewards and pet-evolution rules are all content packs authored in the tool and distributed via the backend — new content ships without code changes (a named requirement).
  • 2D: the dashboard, the route map + ghost, the challenge/leaderboard screens and the virtual pet (states, cosmetics) are custom-rendered. 3D: not needed.
  • Front-end + Back-end: a client/server split — device app + backend for persistence, leaderboards, social and content — the run-upload + content-distribution flows are Application Communication ✅.
  • Custom tools: two — the content-authoring tool (challenges/achievements/progression/cosmetics as data) and the GPS-simulation testing tool (synthetic runs to test ghost racing/challenges/rewards/pet without running).
  • Networking: single-player with async social — runs upload and leaderboards/social sync after the fact, so a real-time Networking System is optional (🔵). External DB: central (pet/runs/leaderboards/social/content). Auth ⏭️ / Analytics ⏭️: accounts + activity analytics are natural but module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — the proposed 6 CS + 1 Design + 0 Art is the module's tight case for an art-heavy concept: a virtual pet with states, cosmetics/accessories and hatch/evolve stages, plus dashboard/map/UI, is a real art surface, so with no artist the single designer must also carry the D11 conditional each milestone, and a solo designer + 0 artists is exactly what the design pool flags ("must ask the instructor which conditional bends", see design-goals-pool.pdf). If the team stays 0-artist, scope the art hard: one pet with a few evolution stages and a small, reusable, recolourable cosmetic set authored/sourced under D11, and expect the instructor sign-off on the bent conditional. Scope note (advisory): a GPS Activity Engine (noise filtering + ghost interpolation + race events) + a replay/ghost system + persistence/social/leaderboards + a data-driven content pipeline + two tools is a large, server-backed CS scope — GPS→distance/pace, one recordable ghost with ahead/behind, basic pet progression and one editor is the M1/M2 floor; friends' ghosts, the full social/leaderboard layer, pet evolution and all cosmetics/challenges are the stretch. The content-pack pipeline + the GPS-simulation testing tool are the smartest levers — they let a small team add content as data and test without running.
