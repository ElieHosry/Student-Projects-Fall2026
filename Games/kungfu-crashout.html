Kungfu Crashout (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Kungfu Crashout is a mobile multiplayer fighting game where the environment is the weapon — players pick up items from the background and use them against opponents. Control is screen-based gesture input with no on-screen buttons, a simple scheme that's easy to pick up. Gameplay is quick 1-on-1 battles in a wide side-view stage with detailed, interactable backgrounds; matches last a few minutes. A roster of characters each have unique fighting styles, players combining the environment with their martial-arts skills to win. Named load-bearing C++: a native Android build; a C++ game loop holding a stable 60 fps with 2 characters + multiple physics objects + particles, running deterministically; peer-to-peer PvP; AI opponents; and interactable stage objects. Named technical features: gestures as player actions (movement, attacks, interactions); environmental interactions (pick up + throw objects); different enemy AIs (difficulty / character-based); and multiplayer PvP. Tools: a custom editor to view/debug the game — hurtbox/hitbox debugging + frame checking of movement and animation, a debug/admin menu to adjust values, an (extra) keyframe editor if time allows, and a JSON serializer. Design features: the stage/arena determines available environmental items; a roster of ≥6 unique characters; the gesture input system simplifying combos/specials; and a wide variety of interactable items. Team: 6 CS + 1 Design + 2 Artists.

Note (module completeness): the proposal doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist unlocked characters / cosmetics / match records there (a standard, small addition; see the External Database row + M1G12-style integration). Monetization: none is specified — if added, keep it cosmetic / non-pay-to-win (no selling characters/power that affect the fight) per the module's clean-monetization rule.

References:

  • Super Smash Bros. Ultimate — Wikipedia (the benchmark fighter built around items and stage hazards as weapons — fighters grab, throw and weaponise the environment on a wide side-view stage — the environment-is-the-weapon precedent)
  • Brawlhalla on Steam (a free-to-play platform fighter with a large roster of unique "Legends" and weapon pickups, running cross-platform including mobile — the roster-of-distinct-fighters + pick-up-a-weapon + clean F2P precedent)
  • Shadow Fight 3 — Google Play (a popular mobile martial-arts fighting game with a simplified touch-control scheme and distinct fighting styles/factions — the mobile + simple-touch-combat precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — the game is explicitly a native Android build with gesture (no-button) touch controls. The Native PC build is the development/tools vehicle (the hurtbox/frame-debug editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts, unlocked-character/cosmetic persistence and match records; peer-to-peer is the in-match transport.
Front end: A 2D side-view fighter renderer — the two characters (animated with frame data), the detailed interactable stage, the pick-up/throwable items, hit-spark VFX and particles, and the minimal gesture-driven HUD. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The deterministic real-time C++ fight engine — the fixed-timestep loop holding 60 fps with 2 characters + physics objects + particles, hitbox/hurtbox collision + frame data, the grab/throw/environmental-object physics, the gesture-to-action recognizer, and the enemy AIs — plus a peer-to-peer netcode layer for PvP; Firebase for accounts/persistence on the Extended tier. Languages: C++ (engine + netcode); Firebase-backed services on the Extended tier.
Backend scope: Local + P2P now, server-ready (T2) — the accounts/persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the deterministic C++ loop is the heart — it advances both characters, resolves hitbox/hurtbox collisions on frame data, simulates the throwable physics objects + particles, and holds 60 fps on the Native-Android target.
  • Networking: core feature — peer-to-peer PvP. Note this is the hardest part of a fighting game: a deterministic lockstep/rollback netcode over P2P is a serious undertaking, so the local 2-player + AI fight is the reliable floor and networked PvP is the primary scope-cut candidate (see scope note). Application Communication ✅ covers accounts/persistence.
  • Data-driven: characters + movesets/frame data, the ≥6 roster, the item catalogue and per-stage item availability are all data — a new character, move or item is a data change (authored/tuned via the editor).
  • 2D: the side-view fighter renderer, the detailed interactable stage, throwable items, hit-spark VFX and particles (custom-rendered). 3D: not needed.
  • Custom tool: the fighting-game debug editor — hurtbox/hitbox visualization, frame checking of movement + animation, a value-tuning admin menu, a JSON serializer, and (time permitting) a keyframe editor.
  • External DB: accounts, unlocked characters/cosmetics, match records (Firebase — add this per the module). Auth ⏭️ / Analytics ⏭️: module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 2 Art (9) — as proposed, and well-justified: a fighting game is art- and animation-heavy (a ≥6-character roster each with a distinct style and a full move-set of animations, detailed interactable stages, throwable items, hit VFX), so 2 artists are the right call, one able to specialise in character animation (fighting games live on frame-by-frame animation). A single designer owns the FDD, the gesture control scheme + game feel, the roster/item/stage systems and the AI/difficulty design (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). Scope note (advisory): a deterministic 60 fps fight engine + frame-data animation + hitbox/hurtbox combat + grab/throw physics + a debug editor is already a full CS scope for M1/M2 — and peer-to-peer rollback netcode is, on its own, one of the hardest problems in games. Strong recommendation: make the local 2-player + AI fight the floor (fully playable, great feel, ≥3 characters, one or two stages), and treat networked P2P PvP as the stretch (M2G7) — do a networking spike early to de-risk it, and keep the sim deterministic from day one so rollback stays possible. The ≥6 roster, the full item variety and online PvP are the M2 stretch, not the floor.
