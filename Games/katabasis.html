Katabasis (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Katabasis is a level-based macabre-themed RPG where players control three characters in turn-based battles. At the start of each battle, players assign a card to each character granting offensive/defensive abilities; then, based on each character's individual action value, players tap and drag from each character across enemies to chain attacks. Named technical features: a decision-tracking enemy AI that attacks automatically, evaluates the player's likely next action and counters it to force optimal play; a level editor for asset placement and building scenes; a custom particle-effect (VFX) inspector (spawn rate, color-over-time, scale); and a gesture input system (swipes, multi-finger triggers). Load-bearing C++: a real-time combat simulation loop holding a stable update rate across multiple enemies, AI behaviours, environment, repeated attacks and effects on target Android devices; and static memory allocation & pooling (a fixed number of enemies/particles/assets allocated at level load and recycled). Tools: a level editor (scenes, parallax, show/hide images), a particle-effect inspector (sliders for particle patterns), and an asset importer & optimization pipeline (import .mp3/.png etc., convert to engine format, compress). Built for Android — C++ rendering via OpenGL ES, connected to a Kotlin app through JNI. Design features: ≥5 turn-based combat encounters with designed enemy layouts; ≥5 ability cards; ≥3 deployable units with individual action values; and the tap-and-drag chain-attack system.

Note (module completeness): the proposal doesn't mention an External Database or accounts, but the module mandates Firebase as the external DB — plan to persist progress / unlocked cards / level records there (a standard, small addition; see the External Database row + M1G12-style integration). Not a category concern; just build it in.

References:

  • Slay the Spire on Steam (the benchmark card-driven turn-based combat RPG — assign cards that grant abilities, then resolve attacks against a lineup of enemies — the card-ability-per-turn precedent)
  • Darkest Dungeon on Steam (a macabre/gothic turn-based party RPG — lead a small party through level-based encounters with an innovative strategic turn system — the macabre-theme + party-turn-based precedent)
  • Honkai: Star Rail — "Follow-Up Attack" (a turn-based combat system where each character's action value governs turn order and abilities chain follow-up attacks across enemies — the action-value + chain-attack precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ via JNI rendering through OpenGL ES, Kotlin app shell; device: Pixel 9a) — the tap-and-drag chain and gesture input are touch-first; the Native PC build is the development/tools vehicle (the level editor, particle inspector and asset importer). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts and progress/card-unlock persistence.
Front end: A 2D macabre renderer — the three characters, the enemy layouts, parallax scenes, the card-assignment UI, the action-value/turn HUD, the tap-and-drag chain-target overlay, and the particle VFX. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The real-time C++ combat simulation loop (turn/action-value resolution, card abilities, chain-attack targeting, the decision-tracking enemy AI, particle updates), with static allocation + object pooling for enemies/particles/assets; plus Firebase for accounts + progress persistence. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts / progress-persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — it resolves the action-value turn order, applies card abilities, executes the tap-and-drag chain attacks, runs the decision-tracking enemy AI and updates particles, holding a stable rate on Android with static allocation + pooling.
  • Data-driven: cards (≥5), characters/units (≥3, with action values), enemies and their layouts, encounters (≥5) and particle-effect definitions are all data — a new card, enemy or encounter is a data change (authored via the editor tools).
  • 2D: the macabre renderer, parallax scenes, the chain-target overlay, the card/turn UI and the particle VFX (custom-rendered). 3D: not needed. Networking: single-player; accounts/progress persistence is async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵).
  • Custom tool: three — the level editor (scenes/parallax/asset placement), the particle-effect inspector (spawn rate / color-over-time / scale sliders), and the asset importer & optimization pipeline (import + convert + compress).
  • External DB: progress, unlocked cards and level records (Firebase — add this per the module). Auth ⏭️: optional accounts. Analytics ⏭️: optional — encounter win/loss + card usage for balancing.

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 2 Art (9) — a macabre RPG reads by its characters, enemies, cards and scenes: three characters, ≥5 enemies with designed layouts, ≥5 card illustrations, macabre parallax environments and the attack VFX are a large art surface, so two artists carry it; a single designer owns the card-ability design, the action-value/chain-attack systems, the ≥5 encounters and the counter-AI difficulty design (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). Scope note (advisory): a real-time combat loop + decision-tracking AI + card/chain systems + three editor tools + pooling is a full but well-structured scope — the action-value turn combat with the chain attack, ~3 cards, the counter-AI and the level editor is the M1/M2 floor; the full card set, all encounters, the particle inspector and the asset pipeline are the stretch.
