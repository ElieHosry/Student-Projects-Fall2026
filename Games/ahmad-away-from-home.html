Ahmad: Away from Home - Team26 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-22 · Status: awaiting instructor approval

Proposal (as submitted): Ahmad: Away from Home is a puzzle-based exploration game (in the style of a map-piecing game): players zoom out to a world map to place and connect puzzle pieces, then zoom in to explore each piece as a fully navigable environment, hunting for clues and more pieces until a completed section reveals the way out. Named load-bearing C++: a game loop handling player input, NPC AI, collision detection, puzzle fitting and game-state transitions in real time, maintaining a consistent map layout from the pieces with instant feedback. Named technical features: an Undo/Redo puzzle-placement system (track placements, undo/redo without losing collected pieces/progress); Real-Time World & Progression Synchronisation (discoveries during exploration — clues, pieces, objectives — update the world map live); Automatic Terrain-Connection Detection (auto-identify connected same-terrain areas, plus tile preview + placement prediction showing valid positions and resulting connections); and a Multi-State Gameplay System (smooth transition from the 2D puzzle-piecing view to the top-down exploration view). Tool: a Game-State Debugging Tool to visualise the current puzzle map, found pieces, objectives and exploration states, keeping pieces + environments in sync and cutting manual setup. Design features: a rotatable piece-fitting mechanic (rotate + place pieces into matching shapes, any order as long as the shape fits); seamless zoom transition; an environmental clue system (≥4 NPCs + environmental signs — worn paths, notes, landmarks — giving subtle non-handholding hints; ≥4 distinct puzzle-piece biomes — water, forest, ruins… — each with unique interactables/hazards); and free-roam exploration within each piece. Team: 6 CS + 1 Design + 1 Artist.

Note (module completeness): the proposal doesn't name a platform — the zoom/place/rotate interaction is touch-friendly, so it's planned as a mobile build (Native Android, Pixel 9a; a Web-on-mobile build is a viable alternative). It also doesn't mention an External Database or accounts, but the module mandates Firebase — plan to persist save games / progress there (a standard, small addition; see the External Database row + M1G12-style integration). Neither is a category concern.

References:

  • Carto on Steam (a tile-placement adventure where you discover pieces of the world map, rearrange and rotate them (edges must match) to shape the levels, then explore them on foot — an almost feature-for-feature precedent for the place-and-connect-then-explore loop)
  • Dorfromantik — Wikipedia (a tile-placement puzzle of placing/rotating tiles so terrain edges match, forming connected landscape groups — the automatic-terrain-connection + placement-prediction precedent)
  • Gorogoa on Steam (a puzzle of arranging and zooming into panels/tiles to connect them and open paths — the seamless-zoom + piece-arrangement precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — zoom/place/rotate + top-down movement are touch-first; a Web-on-mobile (Emscripten→WASM) build is a viable alternative. The Native PC build is the dev/tools vehicle (the game-state debug + environment editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for save-game / progress persistence.
Front end: A 2D game with two views — the zoomed-out world map (puzzle pieces + connection previews) and the zoomed-in top-down explorable environments (Ahmad, NPCs, interactables, clues) — with a seamless zoom transition and the objective/clue HUD. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; some screens (menus) can be pure Native UI. Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The real-time C++ engine — player input, the puzzle-fitting + rotation + placement-validation, automatic terrain-connection detection, the undo/redo command stack, NPC AI + top-down collision, the multi-state (map↔exploration) machine and the world/progression sync — with instant feedback; plus Firebase for save/progress. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the save/progress seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — it validates + rotates + fits puzzle pieces, runs automatic terrain-connection detection, maintains the undo/redo command stack, drives NPC AI + collision in exploration, and transitions the multi-state (map↔︎walk) machine with instant feedback.
  • Data-driven: the puzzle pieces + their terrain edges, the ≥4 biomes and their interactables/hazards, the ≥4 NPCs + clue placements, and objectives are all data — a new piece, biome or clue is a data change (authored in the debug/environment tool).
  • 2D: both views (the world-map puzzle + the top-down exploration) and the zoom transition are 2D and custom-rendered. 3D: not needed.
  • Custom tool: the Game-State Debugging + environment tool — visualise the puzzle map, found pieces, objectives and exploration states, and author pieces/environments/clues, keeping map + environments in sync.
  • Networking: single-player; save/progress is async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵). External DB: save games / progress (Firebase — add per the module). Auth ⏭️ / Analytics ⏭️: module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — as proposed, and well-matched: an exploration game leans on its environments (≥4 distinct biomes, Ahmad + ≥4 NPCs, interactables, the world-map art, UI), which one dedicated artist can carry, while a single designer owns the FDD, the puzzle/mechanic design, the biome/clue/level design and the exploration pacing (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the biome + clue content outgrows one designer, consider a 2nd designer. Scope note (advisory): a puzzle-fitting + terrain-connection engine + a multi-state/zoom system + free-roam exploration with NPCs + a debug/environment tool is a solid, cohesive scope — the place/rotate/connect mechanic, the seamless zoom, and one or two fully explorable biomes with basic clues is the M1/M2 floor; all ≥4 biomes with unique interactables/hazards, the full ≥4-NPC clue web and the polished world reveal are the stretch. The automatic terrain-connection detection + placement prediction is the trickiest CS bit — validate it early on a small piece set.
