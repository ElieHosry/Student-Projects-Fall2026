oKAI - Team25 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A top-down endless survival bullet-hell for casual mobile players, built around drawing symbols on the touchscreen to cast spells and surviving endless enemy waves. Defeating enemies grants new spells, so the player adapts their strategy as the run progresses; 1–4 players can team up. Named technical features: a custom C++ gesture-recognition engine (geometric template matching — $1 Unistroke / $Q — with a multi-stage preprocessing pipeline: resampling to a fixed point count, rotational normalization, scale-invariant bounding-box scaling, centroid translation; Euclidean scoring against templates; target >90% recognition within a 100 ms latency window); server-authoritative C++ multiplayer for 1–4 players over LAN or cloud (clients send inputs/cast requests, the server owns players, enemies, spells, damage, drops and progression, sends periodic world snapshots; clients interpolate remote entities and use client-side prediction + server reconciliation for the local player; RTT/loss/bandwidth diagnostics; tested under simulated latency/jitter/loss); a data-driven ECS (spell/enemy/player attributes from external files, runtime add/remove/replace of components, systems parallelizable); and a robust modular spell system (spells do more than one-shot damage; fast authoring of unique effects). Core requirements name an external data source, a stable-30fps C++ loop (20+ enemies, 5+ spell objects), an event/snapshot application protocol, CI, JSON+XML data-driven architecture, a dedicated C++ authoritative back-end, and tools: an ECS diagnostics logger, an in-engine gameplay-telemetry API, an in-system game editor with developer diagnostics, and a custom gesture-template editor (draw a symbol, export as XML) to add/refine spell recognition. Development environment: Native Android. Design features: gesture-based spellcasting (the primary mechanic), ≥5 spell types, ≥3 enemy types (Basic / Ranged / Tank), and ≥1 boss.

References:

  • Vampire Survivors on Steam (the endless-survival "be the bullet hell" loop — defeat waves, collect new weapons/abilities each run, snowball your build; now with up to-4-player co-op — the survival-and-adapt loop precedent)
  • Magicka on Steam (a dynamic spell-casting action game where the spell input itself is the mechanic, with up-to-four-player co-op and a wave-survival challenge mode — the input-driven-magic + co-op precedent)
  • Arx Fatalis — Wikipedia (spells cast by drawing runes with mouse gestures that must be drawn correctly to fire — the direct gesture-recognition-to-cast precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — the stated dev environment; device: Pixel 9a) — the touchscreen gesture-drawing mechanic is native-touch-first; the Native PC "desktop diagnostic" build is the development/tools vehicle (ECS diagnostics, telemetry, editors). Extended: a Linux server the team sets up by M2 (full use T2) hosting the dedicated C++ authoritative game server for cloud lobbies + an external database (Firebase or a server-side store) for player/enemy/spell data.
Front end: A top-down 2D bullet-hell renderer (20+ enemies + 5+ spell objects on screen at a stable 30 fps), the live **gesture-drawing surface** (stroke capture + trail feedback + recognized-spell cue), the spell/HUD overlays and the lobby screens. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES drawn in a GLSurfaceView for the realtime 2D; Web/desktop — SDL2/3 + OpenGL ES for the PC diagnostic build.
Back end: The dedicated **C++ authoritative server** (LAN or cloud) running the gameplay simulation for 1–4 players — validating inputs and cast requests, simulating players/enemies/spells, resolving damage and server-random loot drops, owning progression, and distributing snapshots + reliable gameplay events — plus the external data store for spell/enemy/player data. Languages: C++ (engine + server).
Backend scope: Local now, server-ready (T2) — the authoritative server + external DB seam set up & basic-tested on the Linux host by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing on two fronts — the fixed-timestep gameplay simulation (20+ enemies + 5+ spell objects at a stable 30 fps, server-authoritative) and the real-time gesture-recognition service (resample → normalize rotation → scale → translate → Euclidean-score against templates, targeting >90% accuracy within 100 ms). This is the defining performant-C++ requirement.
  • Data-driven: spell, enemy and player attributes load from JSON; gesture templates are XML point-sets authored by the gesture-template editor; the ECS adds/removes/replaces components at runtime (e.g. a FlyingComponent mid-run) so new spells and effects are authored as data, not code.
  • 2D: top-down sprite/particle rendering of the bullet-hell (enemies, spells, drops, the boss) plus the gesture stroke/feedback layer — custom-rendered. 3D: not needed. Networking: server-authoritative snapshots + reliable events for 1–4 players, client prediction/reconciliation, RTT/loss/bandwidth diagnostics, tested under simulated latency/jitter/loss.
  • Custom tool: the gesture-template editor (draw → export XML → registered as a castable spell), plus the in-system game editor and the ECS diagnostics logger + gameplay-telemetry API (the "desktop diagnostic core" build).
  • External DB: player/enemy/spell/progression data. Auth ⏭️: player accounts. Analytics ⏭️: the gameplay-telemetry API (quit-points, retry counts, ability usage, tutorial time) — optional/T2 but explicitly designed for.

Proposed new pool goal (requires instructor approval): Gesture Recognition Engine — the $1/$Q template-matching pipeline as its own graded CS goal (currently folded into M1G1 ⭐ core logic + tested in M1G3 ⭐). If approved it would append to the Games pool (e.g. G17) and become the natural home for this signature system; the three picks below remain from the existing pool.

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 2 Art (9) — bullet-hell reads by its VFX and enemy variety, so two artists carry the spell effects, the ≥3 enemy types + boss, the player and the gesture/HUD art; a single designer owns the gesture-spellcasting feel, the ≥5-spell arsenal, the enemy/boss behaviours and the wave/run progression (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the spell/enemy systems and multiplayer balance outgrow one designer, trade the 2nd artist for a 2nd designer. Scope note (advisory): a custom gesture-recognition engine + server-authoritative netcode + ECS + modular spells + ≥5 spells + ≥3 enemies + a boss + the editor suite is a very large surface — treat single-player survival with the gesture engine, ~3 spells, the 3 enemy types and the gesture-template editor as the M1/M2 floor, with co-op multiplayer, the boss and the full arsenal as the stretch.
