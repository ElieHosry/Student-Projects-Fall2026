RBR - Room Bot Rumble (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): RBR is a bot-builder auto-battler: the player creates a battle cleaning bot by allocating points to its statistics and behaviour and attaching gadgets/weapons, then the bots fight until the timer runs out or a bot is destroyed — the higher score wins. It features an asynchronous PVP system with a points-based rating/ranking. Named technical features: async PVP with a points rating; modular bot customisation (gadgets/weapons); customisations with unique behaviours; stat customisation affecting behaviour; and a paint-trail render as the bot moves. Load-bearing C++: a 2D renderer (multiple objects, primitive shapes, images, text), a sound system, an object-based system for AIs/projectiles/components, a game loop updating & rendering objects/projectiles/particles, image-slicing for sprite-sheet animation, a collision system for combat, and a particle system for VFX. Tools: a generic Finite State Machine for bot AI, an Entity-Component System for modular objects, an animation system (sprite-sheet slicing + playback), a UI system (parent-child anchors), and a module maker to create new bot attachments. Design features: the bot-customisation system (weapon/gadget types); player-adjusted stats that also affect behaviour; timer/score-based combat; and an auto-battler where the player watches their built bot fight in a single world map.

References:

  • GLADIABOTS - AI Combat Arena on Steam (build and customise a robot crew, construct their AI/behaviour, send them to the arena and watch it play out — with asynchronous multiplayer and ranked matches; the closest build-a-bot-set-its-behaviour + async-PvP precedent)
  • Super Auto Pets on Steam (an auto-battler where you build a loadout and battle other players asynchronously — Arena mode with no timers, working toward wins/rating — the async auto-battler + rating precedent)
  • Robocraft — Wikipedia (build a combat robot by attaching modular parts and weapons — lasers, launchers, rail guns, melee — then send it into battle; the modular gadget/weapon bot-building precedent)

How each requirement applies:

Platform fit: Main: Native mobile (device: Pixel 9a) and/or Web browser on mobile — an auto-battler + builder is touch-friendly on either; the Native PC build is the development/tools vehicle (the FSM/ECS tooling + the module maker). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts, submitted bot builds, the async-PVP match resolution and the points rating/ranking.
Front end: A 2D renderer (objects, primitives, images, text, sprite-sheet animation) of the bots, gadgets/weapons, projectiles, the paint trail and the world map, plus the anchored UI (the bot-builder screen, stat allocation, combat HUD, leaderboard). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES); Native — Kotlin Native Android UI + C++ via JNI (Android Studio); OpenGL ES in a GLSurfaceView where realtime 2D is needed (no SDL on native).
Back end: The real-time C++ combat simulation loop (FSM bot AI over the ECS, projectiles, collision, particles/paint-trail, timer/score) + the async-PVP service that resolves submitted bot builds and updates the points rating. Languages: C++ (engine + sim); Firebase-backed services + the Linux match/rating host on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts / bot-build submission / match-resolution / rating seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — it drives the FSM bot AI (behaviour derived from stats + attached gadgets), moves/collides projectiles, updates particles + the paint trail, and resolves the timer/score win condition; the async-PVP match resolution runs the same deterministic sim.
  • Data-driven: bots, stat allocations, gadgets/weapons (each with unique behaviours), FSM behaviour definitions and world maps are all data via the ECS — a new module or bot is a data change (authored in the module maker).
  • 2D: the renderer (objects/primitives/images/text/sprite-sheets), the paint-trail, projectiles, particles and the anchored UI (custom-rendered). 3D: not needed. Networking: PVP is asynchronous (submit build → server resolves → rating updates), so it's async client↔︎server (Application Communication ✅) and a real-time Networking System is optional (🔵).
  • Custom tool: the module maker (author new gadgets/weapons/attachments + their behaviours and stats as data) — plus the FSM/ECS/animation/UI systems as reusable engine tooling.
  • External DB: accounts, submitted bot builds, match results and the rating/ranking. Auth ⏭️: accounts for PVP/rating. Analytics ⏭️: optional — build/win-rate stats for balancing.

Track Goals & Team Composition

Recommended composition: 6 CS + 2 Design + 1 Art (9) — a bot-builder auto-battler is a systems-and-balance game, so the design surface is large (the stat/point economy, the gadget/weapon behaviours, the FSM behaviour design, the rating/matchmaking and combat balance), fitting two designers; one artist can carry a modular, combinatorial bot look (chassis + interchangeable gadgets/weapons parts), the single world map, projectiles/paint-trail VFX and the builder UI (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the modular-part art volume outgrows one artist, trade the 2nd designer for a 2nd artist. Scope note (advisory): an FSM/ECS engine + combat sim + module maker + async-PVP + rating is a full but well-structured scope — the build-a-bot → deterministic auto-battle → score loop with a handful of gadgets and the module maker is the M1/M2 floor; the full async-PVP rating ladder and broad module variety are the stretch. Keep the combat sim deterministic so async matches resolve identically on the server.
