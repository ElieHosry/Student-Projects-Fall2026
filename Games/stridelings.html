Stridelings - Team24 (student proposal)

Assessment: ✅ Fit · Category: Games (gamified-app lens) · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Stridelings is a gamified fitness-tracking app that turns walks and runs into a creature-collecting game without interrupting the workout. A tracked session records distance, pace, route and time, with a chosen Strideling as companion. The Singapore map is gamified into a biome grid (4 biome types), each biome with its own resources and Stridelings of various rarities; resources auto-gather as the user moves and Stridelings follow with interest. At session end, the user keeps the Stridelings that followed to the end and levels their companion by the session; gathered resources decorate a home base where creatures hang out. Biomes rotate weekly, pushing new routes; daily/weekly missions tailored to the user's goals reward consistency. Named load-bearing C++: a real-time GPS signal-conditioning pipeline (Kalman-style filtering/smoothing of noisy GPS + spoofing/abnormality detection); a real-time 2D map render via OpenGL ES from GeoJSON queried from a PostgreSQL + PostGIS server; offline session recording (local SQLite) synced to the server at session end for validation + reward issue (so recording survives tunnels/deadzones); and a data-driven content pipeline (all Stridelings, biomes, resources and drop tables defined externally, edited in the team's editors, exported as versioned content packs, shipping content without code changes). The sim loop reads GPS to update distance/pace, determine the current biome, decide resource collection and creature joins. Tools: a creature-creation tool (spritesheets, stats, spawn, rarity); a session simulator (synthetic GPS traces treated as real sessions with real rewards, for dev testing); a biome editor (biome art + collectible resources); and a debugger/logger (location/updates, biome changes, creature encounters, rewards, missions, system errors). Design features: an interaction-free session (stats screen + map screen with creatures visibly joining, easy switch); the grid-based rotating biomes; creature collecting (unique companion passives — e.g. more resources / rarer encounters — level-ups unlock passives, duplicates fuse to enhance); and the home base (tap-to-interact creatures + furniture bought with gathered resources). Team: 6 CS + 1 Design + 0 Art.

Note (category): like other gamified apps, Stridelings is filed under Games (there is no separate fitness/health category) — assessed through the gamified-app lens (session/economy/retention systems), the same way the module treats step-and-pet and habit-loop projects.

Note (module completeness): the proposal's server is PostgreSQL + PostGIS on the team's Linux server — exactly the module's Extended tier (a Linux server set up by M2, full use T2). Firebase is the module's default external DB; the team may use it for auth/accounts or keep PostGIS as the primary store (either is fine — just set the seam up + basic-test it by M2). Monetization: none is specified and the economy is earn-by-exercise (resources → furniture), which is clean; if real-money purchases are ever added, keep them cosmetic / non-pay-to-win (no buying rarity or power) per the module's clean-monetization rule — worth stating explicitly given the rarity/fusion systems.

  • Pokémon Go — Wikipedia (the location-based creature-collecting benchmark: a gamified real-world map with creatures to encounter and collect as the player moves through GPS space — the map-as-game-board + collect-by-moving precedent)
  • Zombies, Run! — Google Play (the benchmark gamified running app that layers a game over the run without interrupting the workout, rewarding consistency through missions — the non-interruptive-fitness-game precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI, OpenGL ES map rendered in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — GPS, background-safe offline recording and on-device SQLite are native concerns. The Native PC build is the development/tools vehicle (the creature-creation tool, biome editor, session simulator and logger). Extended: the team's Linux server + PostgreSQL/PostGIS (set up by M2, full use T2) serving GeoJSON + validating sessions and issuing rewards; Firebase optionally for auth/accounts.
Front end: A 2D app — the interaction-free session (stats screen + the OpenGL ES map with the biome grid and Stridelings visibly joining), the collection, the companion/level UI and the decoratable home base. Languages: Native — Kotlin Native Android UI + the C++ engine/services via JNI (Android Studio); OpenGL ES for the realtime map in a GLSurfaceView; some screens (collection, home, missions) can be pure Native UI. Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: Two layers. On-device C++: the GPS signal-conditioning pipeline (Kalman filtering + spoof/abnormality checks), the real-time session sim loop (distance/pace, biome resolution, resource collection, creature joins), the map renderer, and the offline SQLite recorder. Server: the Linux + PostgreSQL/PostGIS service that serves GeoJSON, validates uploaded sessions and issues rewards, and hosts the versioned content packs. Languages: C++ (device engine/services); server (Postgres/PostGIS + the team's service layer); Firebase optional.
Backend scope: Local + offline now, server-validated (T2) — the upload/validate/reward seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ sim loop reads conditioned GPS each tick to update distance/pace, resolve the current biome cell, decide resource collection and creature joins, and drive the two session screens; the GPS signal-conditioning pipeline (Kalman filter + spoof detection) is a distinct C++ performant service feeding it.
  • Data-driven: Stridelings (stats/rarity/spawn/passives), the 4 biomes + their resource/drop tables, missions and home furniture are all external content packs — new content ships without a rebuild (this is a named, load-bearing requirement, not an afterthought).
  • 2D: the OpenGL-ES map render from server GeoJSON, the biome grid, the joining creatures, the collection and the home base (custom-rendered). 3D: not needed.
  • Front-end + Back-end: a genuine client/server split — device app + Linux/PostGIS server that validates sessions and issues rewards; the offline-record-then-upload flow is Application Communication ✅.
  • Custom tools: four — the creature-creation tool, the biome editor, the session simulator (synthetic GPS traces), and the debugger/logger.
  • Networking: no real-time multiplayer — sessions upload asynchronously after they end, so a Networking System is optional (🔵). External DB: central (PostGIS + content packs + per-user collections). Auth ⏭️ / Analytics ⏭️: accounts and consistency analytics are natural but module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 1 Art (8) — a creature-collector is an art-heavy genre (many Stridelings across rarities, 4 distinct biomes, home-base furniture, UI), so the proposed 6 CS + 1 Design + 0 Art is the module's tight case: with no artist, the single designer must also carry the D11 conditional (Art POC / Art Implementation Quality) each milestone, and a solo designer + 0 artists is exactly the situation the design pool flags — such a team "must ask the instructor which conditional bends" (see design-goals-pool.pdf). Strongly recommended: add 1 Artist (best for a monster-collector's asset volume), or at least a 2nd designer so one owns the session/economy/retention design and the other absorbs the D11 art surface. If the team stays 0-artist, scope the art hard: a small, reusable, stylised creature/biome set (a few base silhouettes recoloured by rarity/biome; tile-based biome art) authored/sourced under D11, and expect the instructor sign-off on the bent conditional. Scope note (advisory): a Kalman GPS pipeline + a GeoJSON OpenGL-ES map + offline-record-and-validate + a data-driven content pipeline + four tools + a client/server split is a large, server-heavy CS scope — one biome type, basic GPS→distance/creature-join, offline record + a stub validate, and one editor is the M1/M2 floor; the 4 rotating biomes, spoof detection, fusion/passives, the home base and all four tools are the stretch. The content-pack pipeline is the smartest lever here — it lets the (small) team ship creatures/biomes as data without engineering time per item.
