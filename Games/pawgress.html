Pawgress - Team13 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Pawgress is a wellness app that turns everyday walking into play: your steps help a virtual pet grow and stay happy, while your walks gradually reveal areas of Singapore on an interactive map. Set daily walking goals, build a streak, explore new places, and earn rewards to care for and customise your pet. Named technical features: device step-counter synchronisation; GPS-based map exploration (detect explored areas, update map progress); a virtual-pet progression system (walking + milestones → pet EXP, growth, rewards); and offline save & sync (store progress locally offline, sync to backend when reconnected). Loop: a local C++ engine handling rendering logic and loops, the glue between app and backend, data transfer to/from the backend, and update loops for local UI + rendered graphics (the pet avatar). Tools: three debugging tools — a GPS spoofer, a simulated-tracking-data injector (steps, distance), and a network-break inspector (client-sent vs server-accepted). Design features: GPS map exploration; real step tracking; virtual-pet progression & customisation; and daily goals & streaks.

Note on category: filed under Games — Pawgress is a gamified-wellness app (virtual-pet progression, rewards, streaks, exploration), the exact shape the module's Games design pool covers under its gamified-apps lens (Duolingo / Forest / Habitica / Healthy 365 are its benchmarks). Not Visualization & Analytics (it's a pet/exploration game, not a data dashboard) and not Social Media (no social core as written).

Why "with adjustments" (conditions for week-5 approval):

  1. Add a content-authoring tool as the graded Custom Tool. The three listed tools (GPS spoofer, tracking-data injector, network-break inspector) are excellent debugging infrastructure — keep them (they live under G3 ⭐) — but the module's Tools requirement expects a content-authoring tool. Add one, e.g. an editor to author the map exploration regions / Singapore landmarks, the pet growth stages + customisation items, and the reward / milestone / streak rules as data (this becomes M2G2 ⭐, and it directly serves the "later support other workstations / more content" goal).
  2. Keep the C++ loop and 2D rendering load-bearing (avoid CRUD collapse). As written, the risk is that the app becomes a Firebase-backed step counter with a picture of a pet. To be a real module project, the C++ must do real work: an animated, simulated pet (growth/mood/reaction states + reward VFX), a custom-rendered pan/zoom map of Singapore with on-device fog-of-war exploration computed from GPS, and real offline-sync merge/conflict logic — with pet/region/reward definitions data-driven. The step/GPS/Firebase sync is the plumbing, not the deliverable.

With those two in place this is a solid Games (gamified-wellness) project; the pieces (data-driven pet sim, custom 2D map + fog-of-war, offline-sync, a content editor) are all genuine module work.

How each requirement applies:

Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts, the cloud store, and the offline-sync backend.
Front end: The animated pet avatar (growth/mood/customisation), the custom-rendered pan/zoom **map of Singapore with fog-of-war exploration**, and the daily-goal/streak/reward UI. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D (pet + map) in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The local C++ loop (pet simulation + animation, the fog-of-war exploration update from GPS, step ingestion, the local UI/graphics update) + the offline save/sync layer with merge/conflict resolution; plus accounts and the cloud store. Languages: C++ (loop + sync merge); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts / cloud-store / offline-sync seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing once adjustment 2 holds — it simulates and animates the pet (growth/mood/reaction), updates the fog-of-war exploration state from GPS, ingests step data, and drives the local UI/graphics; the offline→online sync merge is real C++ logic.
  • Data-driven: pet growth stages + customisation items, map regions/landmarks + exploration rules, and reward/milestone/streak rules are all data — a new pet, region or reward is a data change (authored via the new content editor).
  • 2D: the animated pet and the custom pan/zoom map with fog-of-war + the goal/streak/reward UI are real 2D rendering (custom-rendered) — this is the 2D gate. 3D: not needed. Networking: offline save + backend sync is async client↔︎cloud (Application Communication ✅), so a bespoke Networking System is optional (🔵).
  • Custom tool: 🔶 the debug tools (GPS spoofer, data injector, network inspector) are supporting infrastructure; add a content-authoring editor (regions/landmarks, pet stages/items, reward rules) as the graded tool (see adjustment 1).
  • External DB: accounts, pet/customisation ownership, exploration + streak progress; local DB for offline. Auth ⏭️: accounts. Analytics ⏭️: optional — activity/retention trends.

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 2 Art (9) — Pawgress lives on charm: the pet (growth stages, moods, expression, a customisation-item catalogue) plus the Singapore map/landmarks and the reward art are a large art surface, so two artists carry it; a single designer owns the progression/reward economy, the exploration design and the daily-goal/streak retention loop (with the wellness ethics line) (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the retention/economy design outgrows one designer, trade the 2nd artist for a 2nd designer. Scope note (advisory): pet sim + fog-of-war map + offline sync + progression economy + a content editor is a healthy but full scope — the pet + one explorable map area + the step→EXP→reward loop + offline-sync + the content editor is the M1/M2 floor; broad customisation, many regions and analytics are the stretch.
