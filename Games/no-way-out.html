No Way Out - Team05 (student proposal)

Assessment: ✅ Fit · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): No Way Out is a 2-player top-down brawler where two scavengers enter shifting labyrinths that mutate unpredictably, racing to collect loot while sabotaging each other's paths. A real-time C++ simulation engine tracks wall directions, collision states and dynamic map shifts every frame so transitions are seamless — no softlocks, no desyncs — and a robust LAN networking layer keeps both players synchronized through every mutation and trap trigger. Named load-bearing C++: the game loop remembers all wall directions each frame then randomises/changes a chosen wall, aiming for a stable step for up to 4 players (targeting 2), running deterministically; and a real-time physics/collision engine that keeps wall collision correct as walls change direction. Named technical features: an algorithm that shifts the layout while guaranteeing a path back to spawn (no softlocking); clean, fast tile updates so players aren't visibly affected by layout changes; robust LAN networking that resists desync through layout changes; and the collision engine for direction-changing walls. Tool: a custom level editor for building maps (environment + traps). Design features: dynamic labyrinth mutation forcing constant adaptation; a loot system with limited carry capacity and deposit scoring; sabotage mechanics (traps, path-blocking, altering the labyrinth); and a timed survival challenge under a strict countdown. Monetization is a cosmetic-only shop (no gameplay effect). Target platform: Native Android mobile, tested on Google Pixel 9a.

Note (module completeness): the proposal doesn't mention an External Database or accounts, but the module mandates Firebase as the external DB — plan to persist cosmetic ownership / unlock records (and optionally match results) there (a standard, small addition; see the External Database row + M1G12-style integration). Not a category concern; just build it in.

References:

  • Ultimate Chicken Horse on Steam (a competitive party game where players place traps and hazards to sabotage each other while racing an obstacle course — the place-traps / sabotage-the-opponent precedent; also ships a level editor)
  • SpeedRunners on Steam (a competitive multiplayer race where players use items to sabotage rivals and the last one on screen is eliminated — the race-under-pressure + sabotage precedent)
  • Labyrinth (Ravensburger board game) — Wikipedia (the classic shifting-tile maze: players slide rows of tiles to reshape the labyrinth every turn, opening and closing paths — the mutating-maze precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ engine via JNI rendering through OpenGL ES in a GLSurfaceView, Kotlin app shell; device: Pixel 9a) — a real-time top-down brawler with touch controls; the Native PC build is the development/tools vehicle (the level editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for cosmetic-ownership persistence (and optional match records); LAN peer-to-peer is the in-match transport.
Front end: A 2D top-down renderer — the mutating labyrinth grid, both scavengers, loot, traps, the countdown/score HUD and the deposit/carry indicators, updated seamlessly as walls shift. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The deterministic real-time C++ simulation loop (per-frame wall-direction state, the maze-mutation algorithm with a guaranteed path-back-to-spawn, collision resolution for direction-changing walls, loot/sabotage/trap logic and the countdown), plus the LAN networking layer keeping both clients in sync through every mutation; Firebase for cosmetic ownership on the Extended tier. Languages: C++ (engine + networking); Firebase-backed services on the Extended tier.
Backend scope: Local + LAN now, server-ready (T2) — the cosmetic-persistence seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — each frame it records every wall's direction, mutates the chosen wall(s), re-resolves collision so a turning wall never traps or tunnels a player, advances loot/sabotage/traps and the countdown, and holds a stable deterministic step (targeting 2 players, architected for up to 4).
  • Networking: core pillar — a robust LAN layer (peer/host) keeps both clients synchronized through every maze mutation and trap trigger; determinism + a shared seed for the mutation stream keeps the two simulations identical, with desync detection so a divergence is caught, not silently played out.
  • Data-driven: tile/wall types, trap definitions, loot values + carry/deposit rules, the mutation parameters (seed, cadence, constraints) and the cosmetic catalogue are all data — a new trap, tile or cosmetic is a data change (authored via the level editor).
  • 2D: the top-down maze renderer, the shifting-wall transitions, loot/trap sprites and the countdown/score HUD (custom-rendered). 3D: not needed.
  • Custom tool: the level editor — place environment + traps, define spawn/loot/deposit points and the mutable wall regions, with round-trip JSON so designers build maps without code.
  • External DB: cosmetic ownership / unlock records (Firebase — add this per the module). Auth ⏭️: optional accounts. Analytics ⏭️: optional — match length + sabotage/loot stats for balancing.

Native build: Android Studio (Kotlin Native Android UI + the C++ engine via JNI); OpenGL ES drawn in a GLSurfaceView where realtime 2D is needed — no SDL on native, some screens are pure Native UI.
    • Prerequisites: None — foundation of this project.
    • Feeds into: Every other goal; the maze generator (M1G7), collision (M1G5) and networking (M1G11) run on its tick.
  • G2 ⭐ Data-Driven Architecture of Core Objects / Entity System
    Tech & dependencies
    • Tech: Entity/component model with tile/wall types, trap definitions, loot values + carry/deposit rules, the mutation parameters (seed, cadence, constraints) and the cosmetic catalogue in hot-reloadable JSON — a new trap/tile/cosmetic is a data change.
    • Prerequisites: G1 (loop & entity hooks).
    • Feeds into: M2G2 (the level editor), M1G7 (maze data), M1G5 (collision shapes from tile data).
  • G3 ⭐ Debugging, Profiling, Stress Test & CI
    Tech & dependencies
    • Tech: ImGui overlays (wall-direction state, path-to-spawn validation, LAN frame/input buffer), a per-frame state-hash desync detector across the two clients, Tracy profiling of a full mutation + trap-heavy match to hold a stable rate on Android, and Catch2 tests (deterministic replay, "always a path back to spawn"), on a GitHub Actions Windows+Android matrix.
    • Prerequisites: G1 (loop to instrument).
    • Feeds into: M2G3 (CI hardening); the desync detection M2G7 hardens.
  • G5 Physics & Collision — the real-time collision engine that stays correct as walls change direction.
    Tech & dependencies
    • Tech: A C++ collision system (uniform-grid broadphase over the tile map + resolution) that re-derives wall colliders the instant a wall mutates, so a turning wall never tunnels or traps a player; GLM math, deterministic and identical on both clients.
    • Prerequisites: G1 (loop & tick), G2 (tile/wall data).
    • Feeds into: M2G11 (advanced/continuous collision); the "seamless transitions, no softlocks" pillar.
  • G7 Procedural Level Generation — the maze-mutation algorithm with a guaranteed path back to spawn.
    Tech & dependencies
    • Tech: Seeded RNG + a graph/connectivity check (union-find or BFS/DFS reachability) that shifts the layout each cadence while validating that both scavengers retain a path to spawn/deposit — a mutation that would softlock is rejected or repaired; validation tests prove the invariant.
    • Prerequisites: G2 (maze/tile data model).
    • Feeds into: M2G14 (labyrinth variety/pacing); the replayability + "no softlock" pillars.
  • G11 Networking Foundation — the robust LAN layer that resists desync through mutations.
    Tech & dependencies
    • Tech: Web build: LAN sockets (Winsock2/BSD, or ENet/SDL_net) with a lockstep/shared-seed protocol so both clients run the identical mutation stream, an input/frame buffer, and lobby/host discovery; serialization + a state-hash desync guard. Native build: Android Studio (Kotlin Native Android UI + the C++ engine via JNI); OpenGL ES drawn in a GLSurfaceView where realtime 2D is needed — no SDL on native, some screens are pure Native UI.
    • Prerequisites: G1 (deterministic loop), G3 (desync detection).
    • Feeds into: M2G7 (match sync & prediction hardening); the LAN-sync pillar.
