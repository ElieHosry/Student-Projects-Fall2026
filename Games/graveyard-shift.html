Graveyard Shift - Team06 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: Games · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): Graveyard Shift is a darkly-humorous, fast-paced strategy game: you run a supernatural restaurant in a graveyard serving ghosts, zombies and ghouls. The challenge is seating customers by kind (ghosts with ghosts, etc.) — mix them and tensions rise into chaotic riots, which leave remains you must collect as ingredients for the next day's menu. The loop is service → chaos → resource-gathering: mis-seated customers agitate faster (earlier riots); fail to gather enough ingredients and the restaurant risks financial collapse. Named technical features: an event-based sprite animation system (animation events call functions at specific frames — e.g. a throw frame spawns a projectile + plays a SFX, keeping animation/gameplay/audio in sync without hard-coded timings); a reusable FSM template (start/update/exit) for scenes, player and customers; an entity-component system to avoid inheritance hierarchies; and object pooling for the many projectiles (fixed pool, reused on out-of-bounds/hit). Loop: a real-time C++ fixed-timestep loop using delta-time — each update advances time-of-day, updates each customer's mood, spreads agitation to nearby customers, moves projectiles, checks collisions and updates ingredients; a mixed table drops moods faster, and once mood passes a limit the customer enters the riot state and throws projectiles. Built for Android, C++ rendering via OpenGL ES connected to a Kotlin app through JNI. Tools: an animation tool (load sprite sheets + animation data — triggers, frame rate, start/end frame — via JSON so the team adjusts animations without code) and an entity data editor (create customer types, dishes and entities by choosing components and setting values like mood/patience/speed, so UXGD teammates make e.g. an impatient ghoul without recompiling). Design features: time-of-day mood/riot risk; ingredient collection as the player's "health"; seating arrangement (same-kind vs mixed); and a mood + personality system (personality affects how fast mood drops). Monetization: a list of in-app purchases — items to collect ingredients (vacuum), extra patience / riot-delay (TV comedy, calming dish), larger ingredient-collection area, temporary invincibility, and continue/revive at the current level.

Why "with adjustments" (condition for week-5 approval): the monetization model is pay-to-win and breaks the module's clean-monetization rule. Buying more patience / fewer riots, invincibility, larger collection radius and revives/continues all sell gameplay advantage and reduce difficulty for money — exactly what the rule forbids (no pay-to-win, no manipulative loops). Rework it to cosmetics-only / non-advantage: restaurant and customer skins/decor, cosmetic collector tools, and (optionally) a one-time premium unlock — remove or re-base the patience/invincibility/radius/revive items so they don't confer a competitive or difficulty advantage. This is owned by the M2 Design goal D8. Everything else here is strong: the ECS + FSM + event-based animation + object-pooled projectiles + fixed-timestep mood/agitation simulation is a genuinely solid engine plan, and the two content tools (animation tool, entity data editor) fit the module's tools requirement well.

References:

  • Diner Dash: Hometown Hero — Wikipedia (the seating-and-mood time-management restaurant game: seat customers by matching type, each group has a patience/mood meter that drains, and mis-management costs money — the seat-by-kind + mood precedent)
  • Overcooked on Steam (a chaotic, fast-paced restaurant game where impatient customers "storm out in a huff" if service falters — the chaos-under-time-pressure restaurant precedent)
  • Cook, Serve, Delicious! on Steam (a restaurant sim built on planning a menu, gathering/serving dishes and managing customers under pressure — the serve-and-manage-economy precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — C++ via JNI rendering through OpenGL ES, Kotlin app shell; device: Pixel 9a) — the Native PC build is the development/tools vehicle (the animation tool + entity data editor). Extended: Firebase + a Linux server the team sets up by M2 (full use T2) for accounts, high scores and the (reworked) store.
Front end: A 2D top-down restaurant renderer — the graveyard restaurant, seated customers (ghosts/zombies/ghouls with personality/mood tells), flying projectiles, remains/ingredients, and the day-time / mood / money HUD — driven by the event-based animation system. Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2D in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build.
Back end: The fixed-timestep C++ loop (advance time-of-day, update each customer's mood, spread agitation to tablemates, move projectiles, check collisions, update ingredients), the FSM (scenes + player + customer states), the ECS entities, and the object-pooled projectile system; plus accounts/scores/store. Languages: C++ (engine); Firebase-backed services on the Extended tier.
Backend scope: Local now, server-ready (T2) — the accounts / scores / store seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing and well-specified — per fixed-timestep update it advances the day, updates and spreads mood/agitation across mixed tables, moves projectiles, resolves collisions and updates ingredients, transitioning customers into the riot state past a mood threshold.
  • Data-driven: the ECS + the entity data editor make customer types, personalities, dishes, mood/patience/speed values and animation data all JSON — a new customer or dish is a data change (a UXGD teammate authors it).
  • 2D: top-down sprite rendering of the restaurant, customers, projectiles and remains + the event-based animation system + HUD (custom-rendered). 3D: not needed. Networking: single-player; accounts/scores/store are async client↔︎cloud (Application Communication ✅), so a Networking System is optional (🔵).
  • Custom tool: the animation tool (sprite sheets + triggers/frame-rate/start-end via JSON) and the entity data editor (compose entities from components + values) — two genuine content-authoring tools.
  • External DB: accounts, high scores and the (reworked) store. Auth ⏭️: accounts. Analytics ⏭️: optional — riot/failure/economy telemetry for balancing.

Track Goals & Team Composition

Team composition (set by instructor): 6 CS + 2 Design + 0 Art (8) — this is a systems/strategy game with a large design surface (the seating/mood/agitation/riot rules, the ingredient economy, the day-cycle riot-risk curve, personality tuning, and the reworked monetization), which the two designers own; with no artist, the designers take the D11 conditional as a real graded Design goal each milestone (M1 Art Proof of Concept / M2 Art Implementation Quality — the last Design goal each milestone), which consumes one Design+UI slot per milestone (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). Art-risk flag: a spooky-comedy game is art-forward (the ghost/zombie/ghoul roster + personality tells, the restaurant, dishes, projectiles/remains and riot VFX), so 0 artists is a real risk here — scope the roster small and lean on a strong stylised/reusable direction under D11, or reconsider adding an artist within the D+A ≤ 3 cap by trading a designer. Scope note (advisory): the ECS + FSM + event-animation + object pooling + mood/agitation sim + economy + two tools is a full but well-structured scope — the seat→mood→riot→collect loop with the 3 factions, the two tools and the economy is the M1/M2 floor; broad personality/dish variety and the day-cycle depth are the stretch.
