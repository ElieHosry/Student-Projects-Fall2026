Regularz - Team16 (student proposal)

Assessment: 🔶 Fit with adjustments · Category: GovTech · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): A mobile pickup-ordering app giving small Singapore F&B businesses a direct brand channel (vs commission-heavy marketplaces like Grab/Foodpanda or generic POS terminals). Customers browse meals/drinks with live stock, order made-to-order food, and get collection ETAs from a C++ queue-estimation service (moving-window / rolling-average of per-item prep time against the active-order backlog). Collection-only: a UUID order-bound QR code is generated after payment and scanned on the vendor device to confirm pickup. Inventory updates concurrently and safely (DB transactions reserve/restore stock, preventing overselling the last item). A data-driven CRM uses purchase histories to deliver personalized rewards (not flat points). Load-bearing C++: a cloud-hosted queue-management service on Linux that manages the live order queue, verifies payment/kitchen-status updates, computes ETAs, and stores order/ETA data in Firebase with transaction-safe atomic processing, pushing real-time updates to customer phones and the vendor tablet (mobile web). Custom tool: an F&B Operations Editor (staff preview/modify stock, add/remove menu items, edit loyalty rewards, customize the interface). CI/deployment flow with staging→production and regression gates. Design features: branded mobile menu, end-to-end pickup ordering with live collection tracking + QR, vendor dashboard (orders/inventory), and personalized loyalty (a virtual wallet tracking purchases/rewards).

Category note: filed under GovTech — the load-bearing spine mirrors GovTech's "queue management" example (simulate/track a queue, real-time dashboard, service-flow/ops editor) as a two-role service platform (customer + vendor, order → prepare → ready → collected workflow with status tracking). Runner-ups: CMS (its "restaurant menu & ordering" example — menu authoring + customer ordering) and Fintech (payment/wallet/transaction-safe), which fit narrower slices.

Adjustments required for approval:

  • Clear the 2D gate with a custom-rendered data surface. The vendor dashboard (live order queue, inventory, ETA/collection tracking) should be a genuinely custom-rendered OpenGL ES data-display surface (like the GovTech dashboard-rendering goal), not only native widgets/tables — otherwise the app risks collapsing into ordinary CRUD.
  • Payments are mock/sandbox — no real money. Use a simulated/sandbox payment step (no live payment gateway, no real funds), and treat the "virtual wallet" as in-app loyalty points, not real currency. This keeps the project in scope for the module (and out of Fintech's regulated territory).
  • Keep the queue/ETA + concurrency-safe transactions as the team's own load-bearing C++ (which the proposal commits to). The QR order-collection pipeline and the personalized CRM/loyalty engine are novel for this category's civic-flavoured pool — propose them as instructor-approved new pool goals (see below).

How each requirement applies:

Platform fit: Main: Web browser on mobile — the customer app and the vendor tablet both run as a mobile web front end (HTML/JS/CSS + the C++ engine compiled to WASM via Emscripten), touch-first (device: Pixel 9a); the C++ queue service runs on a Linux cloud host. Extended: Firebase + the Linux server (already the home of the queue service) set up by M2 (full use T2).
Front end: The branded menu with live stock, item customization + order flow, live collection/ETA tracking and the QR screen (customer); and the vendor dashboard (order queue, inventory, ready/collected) — with a custom-rendered queue/ETA/inventory data surface (OpenGL ES / WebGL). Languages: Web — HTML/JS/CSS + C++→WASM (Emscripten, SDL2/3, OpenGL ES/WebGL). (Web-on-mobile target — no native app build this trimester; the C++ service is Linux-hosted.)
Back end: The cloud-hosted C++ queue-management service — live order queue, payment/kitchen-status verification, rolling-average ETA computation, concurrency-safe stock reserve/restore, and the CRM/loyalty engine — with Firebase for orders/records/roles and real-time sync. Languages: C++.
Backend scope: Server-indicated (T2) — the Linux-hosted queue service is set up & basic-tested by M2, full use in T2; Firebase is the T1 store/sync bridge.
  • Loop and/or service: the load-bearing piece is a performant C++ service — it maintains the live order queue, computes each order's collection ETA from the active backlog and a rolling average of per-item prep/collection time, verifies payment/kitchen-status updates, and reserves/restores stock with transaction-safe atomic operations (no double-selling the last item, correct restock on cancel) even under duplicate/interrupted requests.
  • Data-driven: the menu/items, stock, prep-time parameters, order states, loyalty/reward rules and the ops-editor interface config are hot-reloadable JSON — the F&B ops editor tunes them without recompiling.
  • 2D: the vendor dashboard (order queue, inventory, ETA/collection tracking) and the customer live-tracking view are custom-rendered data-display UI in OpenGL ES (see adjustment 1). 3D: not needed. Networking: real-time push of order/ETA/status updates to customer phones and the vendor tablet.
  • Custom tool: the F&B Operations Editor — staff preview/modify stock, add/remove menu items, edit loyalty rewards, and customize the interface (a form/flow-builder-style editor).
  • External DB: Firebase stores orders/records/roles and syncs in real time. Auth ⏭️: customer + vendor accounts and roles. Analytics ⏭️: purchase histories drive the CRM/loyalty.
