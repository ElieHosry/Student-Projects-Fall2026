SPACE - Team35 (student proposal)

Assessment: ✅ Fit · Category: Simulator · Assessed: 2026-09-21 · Status: awaiting instructor approval

Proposal (as submitted): SPACE is a web application for large-scale events (conventions, expos) that helps planners design venues while accounting for crowd movement and emergency access. Planners generate a 3D floor plan, place furnishings (booths, signage), and define entry/exit points; the app simulates crowd movement and surfaces problems (movement bottlenecks, poorly-placed signage), so planners can adjust the layout. Named load-bearing C++: a fixed-timestep crowd-simulation loop (updates attendee movement, detects bottlenecks + restricted-access areas); an ECS (DOTS-like, efficient data layout); agent grouping for pathfinding (group attendees to cut cost); and event-driven pathfinding (recompute only when needed, not every frame). Named technical features: floor-plan importing into an editable layout; an interactive 3D venue editor (place furnishings, entry/exit); crowd simulation + overcrowding heatmap; and emergency-scenario / evacuation simulation. Tools: a file-import system (pdf/png/jpeg → canvas layer with reference scale); a 3D spatial editor (drag-and-drop, scaling/rotation, a 3D grid for precise placement + measurement); and a real-time crowd-simulation tool (emergency scenarios — density, pathfinding, evacuation routes). Design features: a 3D interactable floor plan; a real-world measurement + grid system; a drag-and-drop 3D basic-shapes panel; and simulation flow analysis. Team: 6 CS + 1 Design + 0 Art.

Note (category): SPACE spans a 3D authoring editor and density visualization, but its technical spine is a real-time agent-based crowd/evacuation simulation — so it is assessed as a Simulator (the editor sets up the run; the heatmap reads it out). This lands squarely on the Simulator pool (agent behaviour, movement/collision-avoidance, scenario editor, advanced visualization, evacuation behaviour).

Note (module completeness): the app needs to save/load venue plans, scenarios and run results — use the module's external DB (Firebase, or the team's Linux server) for this; set the seam up + basic-test it by M2. Platform: SPACE is explicitly a web application for planners at a desk, so the Main target is the web build (browser, HTML/JS/CSS front-end + a C++ engine compiled to WASM via Emscripten, rendering through WebGL/OpenGL ES) — there is no native-mobile target, so goals below carry the Web build label only.

References:

  • Oasys MassMotion — pedestrian simulation & crowd modelling software (the industry benchmark: a 3D venue authoring + pedestrian-flow simulation tool that surfaces congestion hot-spots as heatmaps and validates fire egress/evacuation for stadia and events — the venue-design + crowd-sim + heatmap + evacuation precedent)
  • Social force model — Wikipedia (the foundational pedestrian-dynamics model: attendees are agents driven by goal-seeking + repulsive social/obstacle forces, which is how bottlenecks and congestion emerge — the crowd-movement algorithm precedent)
  • An evacuation simulator for pedestrian dynamics based on the Social Force Model (arXiv) (a worked evacuation simulator: agents egress a floor plan under the social-force model, exactly the emergency/evacuation-scenario feature — the evacuation-simulation precedent)

How each requirement applies:

Platform fit: Main: Web build — a browser app (HTML/JS/CSS front-end) with the C++ simulation engine compiled to WASM via Emscripten, rendering through WebGL/OpenGL ES; desktop-first (planners at a workstation), responsive web-on-mobile optional. No native-mobile target. The PC is also the dev/tools vehicle. Extended: Firebase (or the team's Linux server, set up by M2, full use T2) to store venue plans, scenarios and run results.
Front end: A browser app — the 3D venue editor (grid canvas, drag-and-drop furnishings/booths/signage, entry/exit markers, scale + measurement), the simulation view (attendees moving) and the overcrowding heatmap + flow-analysis panels. Languages: Web — HTML/JS/CSS shell + the C++ engine as WASM (Emscripten), WebGL/OpenGL ES for the 3D scene and the 2D heatmap; some panels are plain web UI.
Back end: The real-time C++ crowd-simulation engine — the fixed-timestep loop over an ECS (DOTS-like), agent grouping + event-driven pathfinding, movement + local collision-avoidance producing emergent bottlenecks, and the evacuation-scenario model — compiled to WASM and driving the browser view; plus a store (Firebase/server) for plans and run results. Languages: C++ (engine → WASM); Firebase/server on the Extended tier.
Backend scope: Client-side WASM engine now, cloud-persisted (T2) — the plan/scenario/results store set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ fixed-timestep loop is the heart — it advances every attendee-agent (goal-seeking + collision-avoidance), groups agents for cheaper pathfinding, recomputes paths only on demand (event-driven), and continuously flags bottlenecks + restricted-access areas.
  • Data-driven: the venue (walls, booths, signage, entry/exit), the agent populations/parameters, and the scenarios (normal vs emergency) are all data — a new layout or scenario is a data change (authored in the editor, JSON round-trip).
  • 2D: the top-down agent visualization and the overcrowding heatmap / density layers satisfy the 2D gate (custom-rendered, no chart libs). 3D (🔶, strong-students tier): the 3D venue editor + 3D floor plan is the ambitious layer — recommended to keep the simulation itself 2D/top-down (which fully satisfies the gate) and treat 3D as a visualization/editing layer on top, so the 3D scope can flex without risking the core sim.
  • Front-end + Back-end: a genuine split — a web/JS front-end over a C++/WASM engine; save/load + results storage is Application Communication ✅.
  • Custom tools: three — the floor-plan import system (pdf/png/jpeg → scaled canvas layer), the 3D spatial editor (drag-drop, scale/rotate, measurement grid), and the crowd-simulation/emergency-scenario tool.
  • Networking: a single-planner tool — no real-time multiplayer, so a Networking System is optional (🔵). External DB: plans + scenarios + run results (add per the module). Auth ⏭️ / Analytics ⏭️: planner accounts + aggregate run metrics are natural but module-deferred to T2 (🔵).

Track Goals & Team Composition

Recommended composition: 6 CS + 1 Design + 0 Art (8) — as proposed, and defensible: a spatial-planning/simulation tool has a light art surface (UI, iconography, the 3D primitive/furnishing look, the heatmap palette), so 0 artists is far less risky here than for an asset-heavy game — the single designer can carry the D11 conditional (visual identity + in-app art quality) alongside the tool/UX design. That said, a solo designer + 0 artists is still the case the design pool flags ("must ask the instructor which conditional bends", see design-goals-pool.pdf), and the design load here is real (the planner UX, the analysis presentation, the crowd-model realism and scenario design), so a 2nd designer is recommended if the team can — one owns the tool/interaction design, the other the D11 art surface + the flow-analysis presentation. Scope note (advisory): a WASM crowd-sim engine (ECS + grouping + event-driven pathfinding + collision-avoidance) + a 3D editor + import + heatmaps + evacuation is a large, genuinely research-flavoured CS scope — a 2D top-down sim of one venue with basic bottleneck detection + a simple editor is the M1/M2 floor; the 3D editor, floor-plan import, overcrowding heatmap and evacuation scenarios are the stretch. Keep the simulation 2D (satisfies the 2D gate) and treat 3D as the strong-students visualization/editing layer — this is the single biggest scope-risk lever.
