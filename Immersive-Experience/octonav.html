OctoNav - Team33 (student proposal)

Assessment: ✅ Fit · Category: Immersive Experience · Assessed: 2026-09-21 · Status: awaiting instructor approval · Runner-up category: Visualization & Analytics

Proposal (as submitted): An Android app (Android Studio) providing indoor navigation for SIT Block E2 with a real-time 3D / isometric campus view. Users pick a destination and a mobility preference; the system computes an optimal multi-floor route weighted by distance, turn count and accessibility. Campus geometry is captured via dedicated LiDAR walk-throughs; users can report temporary obstructions in real time, feeding live rerouting. The app has login (Google / school email), bottom-tab navigation, a user profile and a local database for search history and saved data. Named technical features: custom 2.5D and 3D visualization of Block E2; a cloud database to share data between devices in real time; a nodes-to-model step that turns LiDAR readings into working models; and a pathfinding engine searching across three axes (X, Y, Z). Core-requirement notes: a frame-bounded C++ loop that each tick pulls in new/buffered LiDAR data, updates the internal structure, and renders the current state to a 2.5D and a 3D viewport. Tools: a raw-sensor → point-cloud conversion tool and an engine inspector (query point attributes; visual debug overlays for octree bounds). Design features: real-time crowdsourced updates on closures/obstacles; dynamic routing on live crowd densities; in-depth 1:1 LiDAR mapping; and accessibility (wheelchair / physically-handicapped) conditional routing.

Note on category: filed under Immersive Experience — the deliverable is an explorable, real-time 3D/2.5D reconstruction of a real building navigated with the team's own engine, matching the category's "virtual campus tour" exemplar. Runner-up Visualization & Analytics (the live crowd-density / route data as moving data) — but OctoNav is a navigable spatial world, not a dashboard, so Immersive Experience is the better home. (Not GovTech: there is no staff/operations side or roles/audit trail.)

Scope & risk note (advisory, not a blocking condition): LiDAR capture → point-cloud → nodes-to-model → octree → 3-axis pathfinding → real-time 3D render → live crowdsourced rerouting is a large, ambitious surface, and this is a genuine 3D project (the "strong students only" row) — the LiDAR/point-cloud → model pipeline is the key risk. Scope the floor to one or two floors of Block E2 from a curated capture, with the C++ loop, the octree + 3-axis pathfinding and the 2.5D/3D view proven; treat the full-building capture, live crowd-density rerouting and cloud real-time sync as the stretch.

References:

  • Google Maps Indoor Maps — Google (official indoor-mapping + multi-floor "Live View" indoor navigation that understands altitude/floors — the multi-floor indoor-wayfinding precedent)
  • Matterport — "A Tactical Guide to LiDAR Room Mapping" (LiDAR walk-throughs turned into an accurate, navigable 3D digital twin of a building — the LiDAR-capture → navigable-3D-model precedent)
  • Mappedin — "Accessible indoor navigation software" (indoor wayfinding with barrier-free / wheelchair routing that prioritizes elevators and avoids stairs — the accessibility conditional-routing precedent)

How each requirement applies:

Platform fit: Main: Native mobile (Native Android — the stated build; device: Pixel 9a) — a touch app with a real-time 2.5D/3D campus view and a bottom-tab shell; the Native PC build is the development/tools vehicle (the conversion tool + engine inspector). Extended: Firebase (cloud DB for real-time cross-device sharing of obstruction reports + crowd density; Google/school-email auth) + a Linux server the team sets up by M2 (full use T2) for the LiDAR point-cloud processing pipeline.
Front end: A real-time renderer of Block E2 in both a **2.5D** and a **3D** viewport (multi-floor geometry, the computed route highlighted, obstruction markers, the mobility-preference and destination UI, bottom-tab nav, profile). Languages: Native — Kotlin Native Android UI + the C++ engine via JNI (Android Studio); OpenGL ES for the realtime 2.5D/3D drawn in a GLSurfaceView; Web/desktop — SDL2/3 + OpenGL ES for the PC dev/tools build (conversion tool + inspector).
Back end: The frame-bounded C++ loop (ingest LiDAR/point-cloud data → update the octree spatial structure → render both viewports) + the **3-axis (X,Y,Z) multi-floor pathfinding** weighted by distance/turns/accessibility + live rerouting from crowd/obstruction data; plus the cloud DB for real-time sharing and the LiDAR point-cloud processing on the server. Languages: C++ (loop + pathfinding); Firebase-backed services + the server pipeline on the Extended tier.
Backend scope: Server-indicated (T2) — the cloud real-time-sync + LiDAR-processing seam set up & basic-tested by M2, full use in T2.
  • Loop and/or service: the C++ loop is load-bearing — each tick it pulls in new/buffered LiDAR/point-cloud data, updates the octree spatial structure, runs any pending 3-axis pathfinding/rerouting, and renders the current state to the 2.5D and 3D viewports.
  • Data-driven: the campus geometry (from the nodes-to-model step), node/edge graph with accessibility attributes, room/destination metadata and routing weights are all data, authored/converted via the tools — a new floor or obstruction is a data change.
  • 2D: the 2.5D viewport, the route/turn overlays, the obstruction markers and the app UI (bottom-tabs, profile, search) are custom 2D rendering — satisfying the 2D gate. 3D: ✅ central — the real-time 3D campus view + the octree/3-axis spatial work (strong-students; the key risk). Networking: the real-time cross-device sharing of reports/crowd density is via the cloud DB (Application Communication ✅), so a bespoke real-time Networking System is optional (🔵).
  • Custom tool: the conversion tool (raw LiDAR/sensor input → the engine's internal point-cloud format) and the engine inspector (query point attributes, octree-bounds debug overlays).
  • External DB: the cloud DB (real-time reports/crowd density, cross-device) + the local DB (search history, saved data). Auth ⏭️: Google / school-email login. Analytics ⏭️: optional — common routes / bottleneck reporting.

Track Goals & Team Composition

Recommended composition: 6 CS + 2 Design + 1 Art (9) — because the campus geometry is LiDAR-captured rather than hand-modelled, the art surface is smaller than a typical Immersive Experience (visual style, materials/lighting, wayfinding iconography and UI), so one artist can carry it; the wayfinding UX is the larger surface (destination/mobility selection, multi-floor route legibility, the crowdsourced-report flow, accessibility conditional routing, onboarding), so two designers own the design + UI/UX (rules: min 1 Design mandated, max 9 total, D+A ≤ 3; see team-formation.pdf). If the visual/material polish per floor outgrows one artist, trade the 2nd designer for a 2nd artist. Note: for Immersive Experience the audio floor is lighter (ambient + UI cues) — a lecturer waiver on heavy BGM may apply for a utility wayfinding app.
